개념부터 차근차근!

행은 그대로, 계산은 함께! 윈도우 함수

GROUP BY와 달리 행을 유지하면서 관련 행을 계산하는 SQL 윈도우 함수를 실습합니다.

OVER는 계산 범위를 정의한다. PARTITION BY는 나누기, 창 ORDER BY는 계산 순서, ROWS/RANGE는 프레임이며 결과 표시 순서는 별도 ORDER BY다.

이 단원을 끝내면

  1. 1GROUP BY 집계와 OVER 윈도우 집계가 결과 행 수에 주는 영향을 설명한다.
  2. 2PARTITION BY, 창 ORDER BY, 최종 ORDER BY를 구별한다.
  3. 3ROW_NUMBER, RANK, DENSE_RANK의 동률을 계산한다.
  4. 4누적합과 최근 N행 집계의 프레임을 해석한다.
  5. 5ROWS와 RANGE의 동률 처리를 실제 예제로 구별한다.
  6. 6UNBOUNDED PRECEDING/FOLLOWING, CURRENT ROW와 LAST_VALUE 기본 프레임을 해석한다.
  7. 7LAG, LEAD, FIRST_VALUE, LAST_VALUE의 경계 결과를 계산한다.
  8. 8NTILE, PERCENT_RANK, CUME_DIST를 구분하고 계산한다.
  9. 9DBMS별 문법 차이와 미검증 구문을 구별한다.
학습 기록을 불러오는 중이에요.
01

각 행을 남기면서 다른 행을 참고할 수 있을까요?

지난 단원 06V에서는 판매 기록을 지역이나 품목으로 묶어 소계와 총계를 만들었습니다. 이번에는 “이 판매가 해당 지역에서 몇 번째인가?”, “직전 판매보다 금액이 늘었나?”를 알고 싶습니다. 원본 판매행을 잃지 않고 다른 행과 비교하는 데 윈도우 함수를 씁니다.

핵심 질문: GROUP BY는 여러 판매행을 하나의 요약행으로 줄입니다. 반면 SUM(amount) OVER(PARTITION BY region)은 원래 판매행 8개를 남긴 채 각 행 옆에 지역 합계를 붙입니다.

금액이 같아도 SQL에 지정한 정렬 키에 따라 같은 순위를 받거나 서로 다른 번호를 받습니다. sale_day는 학습용 가상 판매일 순번입니다. 이 단원은 예제마다 sale_id나 amount처럼 SQL에 적힌 정렬 키를 기준으로 순서를 읽습니다.

02

GROUP BY와 윈도우 SUM의 결정적 차이

GROUP BY region은 지역별로 한 줄씩 세 그룹을 만듭니다. SELECT sale_id처럼 그룹 기준에 없는 개별 판매 ID를 그대로 함께 보여 주기 어렵습니다. 그러나 SUM(amount) OVER(PARTITION BY region)은 개별 sale_id를 유지하면서 지역 합계를 계산합니다.

A2와 A3을 비교 — 둘 다 같은 합계를 사용
방법결과 행 수서울 합계부산 합계NULL 지역 합계
GROUP BY328018030
윈도우 SUM8280 (각 서울행)180 (각 부산행)30

예: SELECT sale_id, region, amount, SUM(amount) OVER(PARTITION BY region) AS region_total FROM sales; 원본 행 수를 유지하는 것은 창 함수의 일반적 특징입니다. 단, 앞쪽 WHERE 필터에서 제거된 행까지 복구해 주는 것은 아닙니다.

A5에서 WHERE amount >= 50은 창의 입력을 먼저 거릅니다. 부산 20원 행이 빠져 윈도우 합계는 160입니다. 위 상위 3행 예제에서는 안쪽 SELECT가 계산한 rn을 바깥 WHERE가 읽습니다.

03

OVER 안의 묶기와 정렬, 바깥 정렬은 달라요

OVER(...)는 어떤 행 집합을 참고할지 정의합니다. PARTITION BY region을 쓰면 서울·부산·실제 NULL 지역이 서로 독립된 창이 됩니다. PARTITION BY를 생략하면 전체가 하나의 창입니다.

ROW_NUMBER() OVER(PARTITION BY region ORDER BY sale_id)의 ORDER BY는 “지역 안에서 번호를 매길 순서”입니다. SELECT 문 맨 끝의 ORDER BY는 “화면에 반환할 행을 보여 줄 순서”입니다. B2와 B3은 반환 순서가 반대여도 같은 sale_id의 part_pos는 같습니다.

  • 같은 쿼리의 WHERE가 입력 행을 거릅니다. GROUP BY와 HAVING이 있으면 그 단계의 결과가 윈도우 계산의 입력이 됩니다.
  • OVER의 PARTITION BY가 입력을 독립된 파티션으로 나눕니다.
  • OVER의 ORDER BY가 파티션 내부 순서와 동률 기준을 정합니다.
  • 프레임을 사용하는 함수는 지정된 범위의 행으로 값을 계산합니다. 예를 들어 LAST_VALUE는 그 범위의 마지막 행을 읽습니다.
  • 쿼리의 마지막 ORDER BY가 결과의 표시 순서를 정합니다.
OVER 구성 요소
구성없을 때있을 때
PARTITION BY전체 하나의 파티션지역 등 키별 분리
창의 ORDER BY순서 없는 전체 집계 또는 함수별 의미누적·순위·앞뒤 행 계산 순서
프레임 ROWS/RANGE함수별 기본 동작계산에 참여하는 행 경계

이 목록은 SQL의 논리적 처리 순서입니다. DBMS가 선택하는 물리적 실행 계획은 달라질 수 있습니다. 지역의 실제 NULL도 하나의 파티션을 구성합니다. 입력 행에서 지역 NULL을 찾으려면 WHERE region IS NULL을 사용합니다.

동률이 있을 때 ROW_NUMBER() OVER(ORDER BY amount DESC)만 쓰면 동률 사이의 번호 배정 순서가 불확정적일 수 있습니다. 유일한 sale_id를 보조 키로 넣어 재현 가능하게 만드세요.

04

공동 2등 다음은 3등일까요, 5등일까요?

ROW_NUMBER는 각 행마다 다른 번호를 매기며, RANK는 공동 순위 다음 번호를 건너뛰고, DENSE_RANK는 건너뛰지 않습니다. 금액을 내림차순으로 정렬하면 100(1행), 80(3행), 50(2행), 30(1행), 20(1행)입니다.

C4의 앞 6행 요약 — ROW_NUMBER만 sale_id로 동률을 나눔
금액행 수ROW_NUMBERRANKDENSE_RANK
1001111
8032 / 3 / 42 / 2 / 22 / 2 / 2
5025 / 65 / 53 / 3

동률 기준을 보존하려면 RANK() OVER(ORDER BY amount DESC)처럼 금액만 정렬합니다. ROW_NUMBER() OVER(ORDER BY amount DESC, sale_id)는 동일 금액에도 고유한 번호를 부여합니다.

쉽게 기억하기: ROW_NUMBER는 각 줄 번호, RANK는 공동 등수+빈 등수, DENSE_RANK는 공동 등수+연속 등수. 이 표현은 STUDY.note의 비공식 기억법입니다.

RANK와 DENSE_RANK의 윈도우 ORDER BY에 고유한 sale_id를 더하면 두 정렬 키가 모두 같은 행이 없어 공동 순위가 사라집니다. 최종 ORDER BY에만 sale_id를 넣으면 출력 순서만 바뀌고 계산한 순위는 유지됩니다.

05

SUM·AVG·COUNT도 OVER를 붙이면 달라집니다

SUM(amount) OVER(PARTITION BY region)은 파티션 전체 금액이고, ORDER BY sale_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW를 더하면 첫 행부터 현재까지의 누적 금액입니다. 서울의 ID 1·2·6·8에서 누적합은 100·150·230·280이고, 파티션 전체 합계는 네 행 모두 280입니다.

서울 매출의 누적과 최근 최대 3행 합계
판매ID금액누적 SUM(D2)최근 3행 SUM(D3)
1100100100
250150150
680230230

D3의 “최근 3행”은 ORDER BY sale_id에서 현재 행과 앞의 최대 두 행입니다. 서울 ID 8에서는 ID 2·6·8의 50+80+50을 더합니다. ROWS 2 PRECEDING은 정렬된 행의 위치를 세므로 판매일이 이틀 전이라는 뜻이 아닙니다. AVG·COUNT에도 파티션과 프레임을 적용할 수 있습니다.

행을 실제로 그룹핑해 줄이는 COUNT(*)와, 개별 행을 남기면서 파티션의 건수를 알려주는 COUNT(*) OVER(PARTITION BY region)은 결과 행 수가 다릅니다.

ORDER BY가 없는 파티션 전체 합계를 누적합으로 잘못 해석하지 마세요. 또한 정렬 키가 고유하지 않으면 ROWS 기반 누적의 동률 사이 순서가 달라질 수 있습니다.

06

ROWS는 행, RANGE는 정렬값의 범위

ROWS는 파티션에서 정렬된 행의 위치를 세고, RANGE는 정렬값과 동률로 범위를 정합니다. E3에서 ROWS의 ORDER BY amount, sale_id는 같은 금액의 처리 순서를 고정합니다. RANGE의 ORDER BY amount는 같은 금액을 동률로 묶습니다.

E3: 서울 50원 동률 2건 비교
판매IDamountROWS 누적RANGE 누적
25050100
850100100

두 50원 판매는 RANGE ORDER BY amount에서 같은 peers이므로 두 행이 동시에 합계에 들어옵니다. 반면 ROWS는 각 행을 하나씩 지나며 50, 100이 됩니다. E4의 RANGE 10 PRECEDING은 “10행 전”이 아니라 “현재 금액 -10 이상”의 값 범위입니다.

E3의 서울 ID 2에서 50과 100이 나온 것은 프레임 종류와 내부 정렬 키 목록이 함께 다르기 때문입니다. RANGE에도 sale_id를 추가할 수 있는 경계에서는 같은 금액이라도 두 정렬값이 달라 동률이 풀립니다. 이 입력에서 RANGE도 두 키를 쓰면 서울 ID 2의 누적합은 50입니다.

E4처럼 RANGE 10 PRECEDING에 값 오프셋을 쓰면 SQLite·Oracle 19c·PostgreSQL 18에서 정렬 키가 하나여야 합니다. E3처럼 값 오프셋이 없는 경계는 PostgreSQL 18과 Oracle 19c에서 여러 키를 쓸 수 있습니다. Oracle 19c는 복수 키를 허용하는 RANGE 경계 네 조합을 명시합니다.

07

현재 행까지일까요, 파티션 끝까지일까요?

UNBOUNDED PRECEDING은 파티션 시작, UNBOUNDED FOLLOWING은 파티션 끝입니다. CURRENT ROW는 ROWS에서는 현재 행, RANGE에서는 현재 행과 같은 정렬값의 동률 범위에 해당합니다. BETWEEN 시작 AND 끝으로 계산 창을 명확히 정합니다.

현재 sale_id기본 프레임 LAST_VALUE(id)전체 프레임 LAST_VALUE(id)

ORDER BY sale_id가 있고 프레임을 적지 않으면, 집계형 창과 LAST_VALUE 등의 기본 프레임은 처음부터 현재 행 및 동률까지입니다. sale_id는 고유하므로 기본 LAST_VALUE(id)는 자신의 ID입니다. 마지막 행 8을 모든 서울 행에서 보려면 ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING처럼 명시합니다.

모든 윈도우 함수가 프레임을 같은 방식으로 사용하는 것은 아닙니다. SQLite에서 ROW_NUMBER·RANK·LAG·LEAD 등은 명시한 프레임을 계산에 반영하지 않지만 FIRST_VALUE·LAST_VALUE와 집계형 창 함수는 반영합니다.

실무와 시험 모두 안전한 습관: “맨 마지막 값”을 묻는 LAST_VALUE는 기본 창을 맹신하지 말고 원하는 마지막 경계를 적습니다.

08

직전 값·다음 값, 그리고 처음·마지막 값

LAG(amount)은 현재 파티션에서 한 행 앞, LEAD(amount)은 한 행 뒤의 값을 읽습니다. 두 번째 인수로 몇 행 떨어졌는지, 세 번째 인수로 해당 위치에 행이 없을 때 사용할 기본값을 정할 수 있습니다.

서울 sale_id 순서의 경계 비교

FIRST_VALUE는 프레임 첫 행의 값, LAST_VALUE는 프레임 마지막 행의 값입니다. G4에서는 서울의 첫 금액이 100, 파티션 전체 마지막 판매 금액이 50인 것을 구별합니다.

LAG의 default는 지정한 거리만큼 떨어진 행이 없을 때 적용됩니다. 그 위치에 행이 있고 대상 열의 값이 SQL NULL이면 NULL을 반환합니다. 이 차이는 DBMS별 NULL 처리 옵션과 구분합니다.

LAG와 LEAD는 프레임 안의 첫·끝을 고르는 대신 파티션 안에서 지정한 상대 위치의 값을 읽습니다. Oracle 19c에는 RESPECT NULLS(기본값)와 IGNORE NULLS 옵션이 있습니다. PostgreSQL 18은 기본적으로 NULL을 건너뛰지 않으며 이 옵션의 구문을 지원하지 않습니다.

09

8개 판매를 타일·백분위·누적비율로 살펴봐요

NTILE(3)은 정렬한 8행을 가능한 한 균등하게 3묶음(3·3·2행)으로 나눕니다. PERCENT_RANK는 (RANK-1)/(파티션 행 수-1), CUME_DIST는 현재 값과 그보다 앞쪽에 있는 값(동률 포함)이 차지한 행 수를 전체로 나눈 비율입니다.

내림차순에서 CUME_DIST의 “누적”은 현재 값 이상인 행의 비율입니다. PERCENT_RANK는 순위를 0~1로 바꾸며 같은 순위는 같은 값입니다. 파티션에 한 행만 있을 때 PERCENT_RANK는 0, CUME_DIST는 1입니다.

NTILE은 동률 값을 무조건 같은 구간에 넣는 함수가 아닙니다. 동률 경계를 여러 타일로 나눌 수 있으므로 H1은 sale_id로 정렬을 결정합니다.

H4의 80원 세 행은 공동 2등이므로 PERCENT_RANK는 (2−1)/(8−1) = 1/7 ≈ 0.142857입니다. CUME_DIST는 100원 1행과 80원 3행을 포함해 4/8 = 0.5입니다. 이 설명의 ≈는 근사값이고, 결과표에는 SQLite 반환값을 그대로 표시합니다.

10

DBMS마다 구문이 같은 부분과 다른 부분

Oracle 19c·PostgreSQL 18·SQLite 3.46.1에는 주요 윈도우 함수와 OVER 개념이 있지만 지원 범위와 옵션은 완전히 같지 않습니다. 이 패키지의 40개 시나리오는 SQLite 3.46.1에서 실제 실행했고 Oracle/PostgreSQL 예시는 공식 문서와 대조한 미실행 참고 구문입니다.

시험에서 비교할 핵심 차이
항목공통 교육 원리주의할 경계
PARTITION BY파티션별 독립 계산NULL 파티션과 SQL 비교의 UNKNOWN은 다름
ORDER BY창 내부 계산 순서최종 반환 정렬은 바깥 ORDER BY
ROWS / RANGE행/값(동률) 기준 프레임함수별 허용·무시 여부 및 다중 정렬키 제한

Oracle의 analytic 함수는 일반적으로 SELECT 목록 또는 ORDER BY에서 사용됩니다. 윈도우 결과를 WHERE로 골라야 할 때는 CTE/서브쿼리에서 계산한 뒤 외부 SELECT에서 필터링하는 패턴을 사용합니다.

같은 SELECT의 WHERE에 윈도우 함수를 직접 쓰면 오류가 납니다. 앞의 상위 3행 예제처럼 안쪽 SELECT에서 순번을 만든 뒤 바깥 WHERE에서 고르면 됩니다. 06X에서는 동률을 포함하는 상위 N 조건도 비교합니다.

공식 원문이 확인되지 않은 “실제 출제 빈도/최신 시험 비중” 표현은 쓰지 않습니다. Oracle/PG 미실행을 기술 통과로 취급하지 않습니다.

중요 개념을 한 장에 정리해요

  • GROUP BY는 그룹당 1행으로 축약하지만, 윈도우 함수는 입력 행을 유지하면서 관련 행을 참조한다.
  • OVER(PARTITION BY ... ORDER BY ...)에서 파티션은 범위, 내부 정렬은 순위·프레임 계산 순서를 뜻한다.
  • ROW_NUMBER는 중복 없는 번호, RANK는 건너뛰는 공동 등수, DENSE_RANK는 연속 공동 등수다.
  • SUM/AVG/COUNT도 OVER를 붙이면 파티션 합계·누적합·이동 집계를 만들 수 있다.
  • ROWS는 행 경계, RANGE는 정렬값/동률을 바탕으로 한 경계다.
  • 기본 LAST_VALUE가 파티션 마지막을 뜻하지는 않는다. 필요하면 UNBOUNDED FOLLOWING을 명시한다.
  • LAG/LEAD는 전후 행, FIRST_VALUE/LAST_VALUE는 프레임 처음·끝을 읽는다.
  • NTILE은 균등 타일, PERCENT_RANK는 상대 순위, CUME_DIST는 동률 포함 누적 비율이다.
  • ORDER BY 없는 결과 행 순서는 보장하지 않으며 DBMS별 지원 옵션을 구별한다.
