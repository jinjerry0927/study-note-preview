DCLData Control Language

개념부터 차근차근!

누가 이 데이터를 볼 수 있을까요? DCL

06AB~06AD에서 데이터를 추가하고, 확정하고, 테이블을 설계했어요. 마지막은 권한입니다. 시험 점수표를 누가 읽고 수정할 수 있는지, 어떤 명령으로 권한을 주고 회수하는지 살펴봐요.

GRANT는 권한 부여, REVOKE는 이전 부여의 회수입니다. 객체 권한과 시스템 권한, 직접 권한과 ROLE 경로, 권한 자체와 다른 사람에게 줄 수 있는 옵션을 구별하세요. 한 경로를 회수해도 다른 권한 경로가 남을 수 있습니다. SQLite 실습은 권한 이력의 교육용 모형이며 실제 DBMS 접근 통제를 수행하지 않습니다.

이 단원을 끝내면

  1. 1DCL이 데이터의 내용이 아니라 접근 권한을 제어하는 SQL 범주임을 설명한다.
  2. 2객체 권한(SELECT/INSERT 등)과 Oracle의 시스템 권한(CREATE TABLE 등)을 구분한다.
  3. 3GRANT 권한 ON 객체 TO 사용자 형태를 해석하고 권한을 가진 대상과 행동을 말할 수 있다.
  4. 4WITH GRANT OPTION으로 부여받는 객체 권한과 타인에게 재부여하는 권한을 구분한다.
  5. 5REVOKE의 기본 구문을 해석하고 다른 역할·직접·PUBLIC 경로가 남는 경우를 판정한다.
  6. 6ROLE과 사용자에게 역할을 부여하는 방식, WITH ADMIN OPTION의 기본 의미를 구분한다.
  7. 7PostgreSQL의 의존 권한 RESTRICT/CASCADE와 Oracle의 세부 차이를 DBMS 문맥 속에서 이해한다.
  8. 8SQLite는 GRANT/REVOKE 문법을 제공하지 않는다는 점과 실습 시뮬레이션 한계를 설명한다.
학습 기록을 불러오는 중이에요.
01

01. 점수표를 아무나 수정해도 될까요?

학과 실습에는 점수표 exam_scores, 출석표 attendance, 공지 notes가 있어요. Alice는 점수표를 읽어야 하지만, 점수를 지우면 안 됩니다. Bob은 입력을 맡았고 Carol은 출석을 봐요. 사용자에게 어떤 작업을 허용할지 정하는 것이 DCL을 배우는 출발점이에요.

같은 표를 두고 담당자별 허용 행동이 다릅니다
대상허용할 행동허용하지 않을 행동
Alice점수표 SELECT점수표 DELETE
Bob점수표 INSERT임의 테이블 삭제
Carol출석표 SELECT점수표 수정

SELECT는 문맥에 따라 DQL로 별도 분류되거나 DML에 포함되지만, GRANT와 REVOKE는 권한을 제어하는 DCL입니다. 교재별 명령 분류 관례와 실제 객체 권한 이름을 혼동하지 마세요.

! 실습과 실제 DB 보안을 구분하세요

SQLite는 사용자/역할 단위의 GRANT·REVOKE SQL을 지원하지 않습니다. 이 단원에서 SQLite로 계산하는 것은 권한 이력표 모형이지, SQLite의 진짜 보안 권한이 아닙니다. 실제 권한의 의미는 Oracle/PostgreSQL 공식 문서에 근거하여 설명합니다.

02

02. 누가 · 무엇을 · 어떤 행동으로?

권한은 주체(사용자/역할) + 대상 객체 + 허용 동작으로 읽으면 쉬워요. GRANT SELECT ON exam_scores TO alice라면 Alice에게 점수표를 읽을 권한을 준다는 뜻입니다.

같은 객체에 줄 수 있는 서로 다른 권한
권한허용하는 행동(일반적인 테이블 문맥)
SELECT행 읽기
INSERT행 추가
UPDATE행 수정
DELETE행 삭제
↳ 핵심 포인트

한 개의 객체 권한을 받았다고 나머지 권한이 저절로 생기지 않습니다. 객체 소유자·상위 권한·스키마 경로의 효과는 DBMS마다 추가 규칙이 있어요.

! 주의

교육용 SQLite effective_access 뷰에는 직접·역할·PUBLIC·소유자 경로가 중복 표시될 수 있습니다. 이는 학습을 위한 “권한 경로 목록”이지 실제 DB 접근 검사 결과가 아닙니다.

03

03. 객체 권한과 시스템 권한의 차이

객체 권한은 특정 표·뷰·함수 등 개별 객체에 대한 동작이에요. GRANT SELECT ON exam_scores TO alice에는 대상 객체 exam_scores가 들어갑니다. 반면 시스템 권한은 데이터베이스 기능·운영 작업을 허용하는 권한이에요. Oracle의 GRANT CREATE TABLE TO alice는 테이블 하나를 지정하지 않는 시스템 권한의 예입니다.

Oracle 중심 시험 대비 비교
구분권한 예구문 특징
객체SELECT ON exam_scores`ON 객체` 있음
시스템CREATE TABLE`ON 특정 테이블` 없음
역할 부여GRANT reader TO alice역할을 사용자/다른 역할에 연결
↳ 핵심 포인트

PostgreSQL은 예컨대 스키마에 CREATE 권한을 부여할 수 있어 같은 “생성” 권한의 범위를 Oracle과 동일한 SQL로 외우면 안 됩니다. DBMS와 권한의 대상을 먼저 확인하세요.

! 주의

GRANT ALL PRIVILEGES ON exam_scores는 그 객체에 적용되는 권한 집합을 뜻합니다. 데이터베이스 전체를 관리할 수 있는 절대 권한과 동의어가 아닙니다.

04

04. GRANT로 권한을 주는 법

Oracle·PostgreSQL의 전형적인 객체 권한 구문은 GRANT 권한 ON 객체 TO 대상;입니다. 한 문장에 여러 권한을 쉼표로 나열할 수 있어요. 예를 들어 GRANT SELECT, UPDATE ON exam_scores TO alice;라면 Alice가 읽고 수정할 수 있습니다. DELETE까지 생기는 건 아닙니다.

문장에서 찾아볼 요소
구문 부분역할
GRANT SELECT어떤 행동을 허용하나
ON exam_scores어느 객체에 대해
TO alice누구에게 부여하나
↳ 핵심 포인트

사례 B1~B3에서는 SQL문을 직접 실행하는 대신 SQLite grants_direct 메타테이블에 부여 이력을 추가해 조회합니다. 실제 Oracle/PG SQL 원문은 referenceSqlNotExecuted와 별도 방언 문서에 보관했습니다.

! 주의

권한을 부여하는 사람도 적절한 소유권 또는 위임 권한이 필요합니다. 아무 사용자나 임의로 GRANT를 실행할 수 있다는 뜻이 아닙니다.

05

05. 읽을 수 있는 권한과 다시 나눌 권한

Alice가 표를 SELECT할 수 있다고 해서 Bob에게 SELECT를 다시 GRANT할 수 있는 건 아니에요. 객체 권한을 다른 사람에게 부여할 수 있게 하는 옵션이 WITH GRANT OPTION입니다.

권한과 위임권한은 별개
Alice 상태점수표 읽기Bob에게 해당 읽기 권한 재부여
SELECT만 직접 받음가능불가
SELECT WITH GRANT OPTION가능원칙적으로 가능 (권한 범위·DBMS 조건 적용)
↳ 핵심 포인트

Oracle의 객체 권한 WITH GRANT OPTION은 일반적으로 사용자 대상이며 역할에는 지정할 수 없습니다. PostgreSQL은 역할과 grant option을 다르게 취급하므로 실제 서버 문서를 확인합니다.

! 주의

WITH GRANT OPTION은 SELECT를 UPDATE로 바꾸지 않습니다. 어떤 권한을 다른 사람에게 넘길 수 있느냐를 바꿉니다.

06

06. REVOKE로 기존 부여를 회수해요

REVOKE SELECT ON exam_scores FROM alice;는 이전에 Alice에게 부여했던 해당 읽기 권한을 회수하는 구문입니다. GRANT의 TO와 REVOKE의 FROM을 대비해 읽어 보세요.

GRANT/REVOKE 짝
권한 부여권한 회수
GRANT SELECT ON exam_scores TO aliceREVOKE SELECT ON exam_scores FROM alice
GRANT INSERT ON exam_scores TO bobREVOKE INSERT ON exam_scores FROM bob
↳ 핵심 포인트

C1~C3의 SQLite 실습은 권한 이력표에서 특정 행을 제거한 결과를 보여 줍니다. 실제 DBMS에서 REVOKE를 실행한 결과로 오인하지 마세요.

! 주의

일부 권한만 회수할 수 있습니다. REVOKE INSERT가 SELECT까지 없애는 명령은 아닙니다.

07

07. 권한 한 개를 회수하면 접근이 항상 막힐까요?

Bob이 점수표 SELECT를 직접 부여받으면서 reader 역할로도 받았다고 해요. 직접 경로만 REVOKE해도 역할 경로가 남아 읽기 접근을 가질 수 있습니다. PUBLIC으로 별도 부여된 권한도 확인해야 합니다.

Bob의 점수표 SELECT 경로
작업직접 경로reader 경로읽기 가능? (개념적 결과)
두 경로 존재있음있음가능
직접 부여만 회수없음있음가능
reader 멤버십도 회수없음없음그 밖의 경로가 없을 때 불가
↳ 핵심 포인트

실습 C4는 직접 부여 INSERT와 DELETE를 차례로 수행한 뒤 ROLE:reader 경로가 1행 남는 것을 확인합니다.

! 주의

실제 권한 계산에는 소유자·상위/관리자 권한·역할 상속 조건 등 DBMS별 세부 규칙이 있습니다. 실습 결과를 모든 DBMS의 보안 판정 엔진으로 일반화하지 않습니다.

08

08. ROLE로 권한을 묶고 위임을 관리해요

학생마다 읽기 권한을 하나씩 부여하는 대신, reader 역할에 여러 테이블의 SELECT 권한을 묶고 사용자에게 그 역할을 부여할 수 있습니다. 사용자의 역할을 회수하면 그 역할을 통한 권한 경로가 사라집니다.

역할과 위임을 구분하기
명칭무엇을 다른 사람에게 부여하도록 허용?
객체 `WITH GRANT OPTION`특정 객체 권한
역할 `WITH ADMIN OPTION`해당 역할의 회원 자격 부여·회수
Oracle 시스템 권한 `WITH ADMIN OPTION`해당 시스템 권한을 다른 주체에 부여 가능
↳ 핵심 포인트

Oracle: GRANT reader TO alice WITH ADMIN OPTION처럼 역할 부여 시 ADMIN을 사용할 수 있습니다. PostgreSQL 18의 역할 멤버십에는 ADMIN/INHERIT/SET 옵션이 분리되어 있고, 이 역할의 실제 권한 사용은 멤버십 옵션의 영향을 받습니다.

! 주의

ROLE을 CREATE하는 작업과 ROLE을 사용자에게 GRANT하는 작업을 혼동하지 마세요. 실제 서버에서는 역할과 사용자·객체가 먼저 준비되어야 합니다.

09

09. 위임한 권한을 회수하면 연쇄 효과는?

Owner가 Alice에게 SELECT WITH GRANT OPTION을 주고 Alice가 Dave에게 SELECT를 다시 주었다고 해요. PostgreSQL에서 Alice의 해당 권한/위임권한을 회수할 때, Dave의 의존 부여가 남으면 기본 RESTRICT는 회수를 거부할 수 있고 CASCADE는 그 의존 부여까지 제거합니다.

PostgreSQL 권한 의존 사례
REVOKE 상황결과
Alice 권한에 의존하는 Dave 권한 존재 + RESTRICT회수 실패 가능
Alice에서 파생된 부여 + CASCADE파생된 부여도 회수
Dave에게 owner가 별도로 직접 GRANT한 경로 존재별도 경로는 유지될 수 있음
↳ 핵심 포인트

E2~E5는 PostgreSQL 의존 관계를 메타테이블 DML로 모의합니다. SQLite에서 REVOKE ... CASCADE를 실행한 적은 없습니다.

! 주의

Oracle의 객체 권한 회수 및 CASCADE CONSTRAINTS 규칙을 PostgreSQL RESTRICT/CASCADE 문법과 동일하게 단정하면 안 됩니다. 다른 시스템 권한·역할 회수의 전파도 DBMS마다 차이가 있습니다.

10

10. PUBLIC과 최소 권한 원칙

PUBLIC은 특정 사용자 이름이 아니라 넓은 대상에게 적용되는 권한 부여 범주로 쓰입니다. 예를 들어 PostgreSQL에서는 모든 역할에 해당합니다. 실습 모형은 notes SELECT를 PUBLIC으로 설정해 모든 가상 사용자에게 한 경로를 보여 줍니다.

권한을 적게 부여해야 사고가 작아집니다
상황나은 방식
점수 조회만 필요해당 표 SELECT만 부여
데이터 수정이 필요하지 않음UPDATE/DELETE를 주지 않음
많은 사용자가 같은 조회 업무역할에 권한 묶어 부여
널리 공개해도 되는 읽기 기능보안 요구를 검토한 뒤 PUBLIC 사용 판단
↳ 핵심 포인트

F1~F5는 PUBLIC 제거와 개별 권한의 유지 여부를 비교합니다. 시험에서는 단순히 REVOKE FROM PUBLIC을 했다고 개별 사용자에게 준 다른 직접·역할 권한까지 회수했다고 판단하지 마세요.

! 주의

시험에서 PUBLIC의 의미와 실무 보안 권장 수준을 혼동하지 마세요. 개인·민감 데이터는 폭넓은 공개 권한 부여를 피해야 합니다.

12. GRANT와 REVOKE를 한눈에 정리해요

  • DCL 핵심: GRANT는 권한 부여, REVOKE는 이전 부여의 회수.
  • 권한 = 주체·대상·동작. 객체 권한과 시스템 권한을 구별.
  • 읽기 권한만으로 다른 사람에게 다시 부여할 수 없음. 객체 WITH GRANT OPTION 확인.
  • ROLE은 여러 권한을 묶어 관리하고, 역할 ADMIN OPTION은 객체 GRANT OPTION과 다름.
  • 직접·ROLE·PUBLIC 등 다른 경로가 있으면 한 경로 REVOKE 후에도 접근 가능.
  • 의존 권한의 RESTRICT/CASCADE는 PostgreSQL 문맥에서 이해하고 Oracle과 구별.
  • SQLite는 GRANT/REVOKE/CREATE ROLE 미지원. 이 단원 40개는 메타데이터 교육 모형.
↳ 핵심 포인트

암기 연결: GRANT → TO, REVOKE → FROM. 다만 정확한 구문과 전파 규칙은 DBMS 기준으로 판단하세요.
