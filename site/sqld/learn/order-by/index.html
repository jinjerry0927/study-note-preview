개념부터 차근차근!

어떤 순서로 보여 줄까요? ORDER BY와 Top N

06P에서는 학과별 학생 수를 계산했어요. 이번에는 결과를 보고 싶은 순서로 정렬해 보고, 점수가 같은 두 학생·NULL 점수·상위 2명 조회에서 왜 보조 정렬과 DBMS 차이 확인이 필요한지 배워요.

ORDER BY가 없으면 반환 순서는 보장되지 않아요. ASC는 기본 오름차순, DESC는 내림차순이에요. 여러 정렬 키는 왼쪽부터 우선하며, 끝까지 동점이면 상대적 순서가 보장되지 않습니다. NULL 기본 위치는 DBMS마다 달라요. Top N은 정렬·동점 처리 기준을 정한 다음 제한해야 합니다.

이 단원을 끝내면

  1. 1ORDER BY의 기본 형태와 ASC·DESC 및 ASC 생략의 의미를 설명해요.
  2. 2두 개 이상의 정렬 키가 동률을 풀어 주는 과정을 실제 행으로 추적해요.
  3. 3정렬 열 이름·SELECT 별칭·출력 위치 번호·표현식을 구별해요.
  4. 4SQLite와 Oracle/PostgreSQL의 NULL 기본 정렬 차이를 이해하고 CASE로 위치를 명시해요.
  5. 5정렬 뒤 LIMIT·OFFSET으로 Top N과 다음 페이지를 계산하고, 동점 포함과 행 수 제한을 구분해요.
  6. 6GROUP BY로 만들어진 집계 결과도 ORDER BY를 별도로 지정해야 함을 설명해요.
  7. 7각 SQL 결과의 행 순서가 왜 그렇게 정해졌는지 복원하고 동점이 남는 경우를 인식해요.
학습 기록을 불러오는 중이에요.
01

01. 같은 학생 6명, 어떤 순서로 볼까요?

06P까지는 학생을 조건으로 찾고, 학과별로 묶어 결과를 계산했어요. ORDER BY는 조회한 행을 어떤 순서로 표시할지 정하는 절입니다. 저장된 원본 행의 순서를 바꾸거나 행을 삭제하지 않아요.

! ORDER BY가 없으면 행 순서가 정해지지 않습니다

예제의 INSERT 순서나 화면에서 우연히 나온 순서를 SQL의 정렬 규칙이라고 가정하면 안 됩니다. SELECT 결과의 순서를 보장하려면 ORDER BY를 명시하세요. 완전한 순서가 필요하면 모든 동점도 구분하는 키를 추가하세요.

02

02. ASC는 작은 값부터, DESC는 큰 값부터

기본형은 SELECT 열 FROM 테이블 ORDER BY 정렬열 ASC|DESC;입니다. ASC는 작은 값에서 큰 값으로, DESC는 큰 값에서 작은 값으로 정렬해요. ASC를 쓰지 않아도 기본은 ASC입니다. 이번 학습시간은 5·6·7·8·9·10으로 모두 달라 순서 차이를 바로 볼 수 있어요.

↳ 정렬은 출력 순서

A1·A2의 ORDER BY study_hours는 조회한 학생 행의 표시 순서만 바꾸며, 테이블의 데이터·학생 ID와 값은 그대로 남습니다.

03

03. 여러 열로 정렬할 때 무엇을 먼저 비교할까요?

ORDER BY exam_score DESC, student_id ASC에서는 먼저 exam_score를 비교하고, 점수가 같을 때만 student_id를 비교해요. 점수 95인 S106은 언제나 90점 학생보다 앞이며, S101과 S103의 동률에서야 두 번째 정렬 기준이 동작합니다.

↳ ASC와 DESC는 키마다 따로 지정

ORDER BY department_id ASC, study_hours DESC는 학과를 먼저 오름차순으로 정렬하고 같은 학과 안에서만 시간을 내림차순으로 정렬합니다. 모든 열에 한 방향이 자동 적용되는 게 아닙니다.

! NULL 학과 순서는 명시해서 재현

M3 실습은 학과가 NULL인 S105를 마지막에 두려고 CASE를 먼저 사용합니다. DBMS 기본 NULL 정렬에 기대지 않기 위한 선택입니다.

04

04. 같은 점수라면 누가 먼저 나올까요?

S101과 S103은 모두 90점입니다. `ORDER BY exam_score DESC`만 쓰면 두 학생 사이의 순서는 보장되지 않아요. student_id ASC를 더하면 S101이 먼저, student_id DESC를 더하면 S103이 먼저입니다. 최종 고유 키까지 지정하면 정렬 결과를 안정적으로 재현하기 쉬워요.

↳ 왜 시험 문제와 실습에 ID를 덧붙일까요?

두 행이 모든 ORDER BY 키에서 동률이라면 DBMS가 어떤 행을 먼저 내놓는지 보장할 수 없어요. 이 패키지의 30개 SQL은 출력 순서를 행 단위로 검증할 수 있도록 필요한 경우 student_id를 마지막에 붙였습니다.

! 동점이 있어도 항상 입력 순서로 나오지는 않아요

동점의 첫 행이 우연히 입력 순서대로 나와도 이를 SQL의 보장으로 가르치지 않습니다. DBMS 실행 계획이나 인덱스 등이 달라지면 결과 순서가 달라질 수 있어요.

05

05. 정렬 열을 이름·별칭·번호로 적어 봐요

ORDER BY study_hours DESC는 열 이름, SELECT study_hours AS hours ... ORDER BY hours DESC는 SELECT 별칭, SELECT student_id, study_hours ... ORDER BY 2 DESC의 숫자 2는 SELECT 두 번째 출력 열을 뜻해요. ORDER BY 2는 study_hours가 테이블의 두 번째 열이라는 뜻이 아니에요.

06

06. NULL 값은 항상 맨 앞이나 맨 뒤일까요?

아닙니다. NULL의 기본 정렬 위치는 DBMS마다 다릅니다. 이번 실습 대상 SQLite는 ASC에서 NULL이 앞, DESC에서 NULL이 뒤입니다. Oracle과 PostgreSQL은 기본적으로 ASC에서 NULL이 뒤, DESC에서 NULL이 앞에 와요. 이 점은 단순한 숫자 오름차순 규칙만으로 결정할 수 없어요.

확인한 기본 NULL 정렬 차이 (변경 가능 설정·타 DBMS는 별도)
DBMSASC 기본 NULL 위치DESC 기본 NULL 위치
SQLite 3.30+앞 (FIRST)뒤 (LAST)
Oracle Database 26ai뒤 (LAST)앞 (FIRST)
PostgreSQL 18뒤 (LAST)앞 (FIRST)
! 표의 모든 DBMS에서 예제를 직접 실행한 것은 아닙니다

SQLite에서 N1~N4를 실제 실행해 검증했습니다. NULLS FIRST와 NULLS LAST는 SQLite 3.30부터 지원합니다. Oracle·PostgreSQL 값은 공식 문서의 기본 규칙을 대조한 것이며 실제 각 서버에서 이 예제를 실행한 결과라고 주장하지 않습니다. 문자 정렬은 collation이나 로캘에 따라 달라질 수 있습니다.

07

07. NULL 위치를 직접 지정해 볼까요?

지원하는 DBMS에서는 ORDER BY exam_score ASC NULLS LAST처럼 NULLS FIRST/LAST를 지정할 수 있어요. 다만 모든 DBMS가 같은 문법을 지원하지는 않습니다. 더 넓게 쓰는 방법은 CASE WHEN exam_score IS NULL THEN 1 ELSE 0 END를 먼저 정렬 키로 두고, 실제 점수를 다음 키로 정렬하는 것입니다.

↳ CASE의 0·1은 정렬을 위한 구분값

C1에서는 NULL이 아닌 행에 0, NULL 행에 1을 주어 0 그룹을 먼저 보입니다. 원래 exam_score를 수정하거나 NULL을 0점으로 바꾸는 것은 아닙니다. 같은 그룹 안에서는 점수와 student_id로 순서를 정해요.

! COALESCE로 0점 처리하는 것과 다른 방법

COALESCE(exam_score,0)는 NULL을 실제 0점처럼 정렬하는 새 계산값을 만들기 때문에, NULL과 0점을 구분하려는 경우에는 CASE 정렬 기준이 더 명확합니다.

08

08. 상위 2명만 보고 싶다면?

Top N은 무엇을 기준으로 상위인지 먼저 정하고 그 순서에서 N개 행만 선택하는 조회예요. SQLite에서는 ORDER BY exam_score DESC, student_id ASC LIMIT 2를 사용합니다. 이 데이터는 S106(95점) 다음 S101(90점)이 나오고, 같은 90점인 S103은 LIMIT 2이므로 제외됩니다.

↳ DBMS별 Top N 문법

SQLite·PostgreSQL에서는 LIMIT 2, Oracle Database에서는 FETCH FIRST 2 ROWS ONLY 등의 구문을 사용합니다. Oracle에서는 기본 DESC에서 NULL이 맨 앞이므로 같은 고득점 상위 예제를 재현하려면 `NULLS LAST`도 명시해야 합니다. 문법과 기본 NULL 위치를 함께 확인하세요.

↳ Oracle ROWNUM은 먼저 정렬해야 정확한 상위 N행

아래 Oracle 전용 비교 예제를 보세요. WHERE ROWNUM <= 2와 ORDER BY를 같은 SELECT에 적으면 상위 점수 2행이 보장되지 않습니다. 정렬을 안쪽 서브쿼리에 먼저 적용한 뒤 바깥 SELECT에서 ROWNUM <= 2를 사용하면 S106(95)·S101(90) 두 행을 선택할 수 있어요. 화면의 두 학생 표시 순서까지 보장하려면 바깥 ORDER BY도 지정합니다. 현대적인 FETCH FIRST 2 ROWS ONLY도 비교합니다. Oracle 실서버 미실행: 공식 문서와 실습 데이터에 기초한 예상 결과예요.

! ORDER BY 없는 LIMIT은 상위 점수를 뜻하지 않아요

정렬 기준을 생략한 LIMIT 2는 그저 반환 행 수를 제한할 뿐, 최고 점수 2명을 보장하지 않습니다. 동점이 있다면 student_id처럼 고유한 보조 키를 붙여 선택 결과를 결정하세요.

09

09. 두 행을 건너뛰거나 공동 2등을 포함하면?

LIMIT 2 OFFSET 2는 정렬된 결과의 첫 두 행을 건너뛰고 다음 두 행을 보여 줍니다. P4에서는 S103(90점), S102(80점)이 나옵니다. 반면 동점자를 함께 포함한다는 조건이면 고유 ID로 2행만 자르는 것과 결과 건수가 달라질 수 있어요.

P5는 SQLite에서 두 번째 행의 비NULL 점수 경계 90을 먼저 구한 뒤, 점수 90 이상인 행을 모두 보여 주는 *이 자료에 한정된 동점 포함 실습*입니다. 결과가 S106·S101·S103의 3행인 이유는 S101과 S103이 둘 다 90점이기 때문이에요. Oracle 등에서 지원되는 FETCH FIRST 2 ROWS WITH TIES는 동점 포함용 별도 문법이며 SQLite에 그대로 붙여 실행하면 안 됩니다.

! 동점 포함의 기준을 잘 정의하세요

행 수 제한과 동점 포함은 같은 규칙이 아닙니다. WITH TIES에서 고유 ID까지 ORDER BY에 넣으면 점수가 같아도 전체 정렬 키가 달라져 동점으로 취급되지 않을 수 있습니다. P5는 현재 자료에서 2등 경계가 NULL이 아닌 90점이라는 점을 이용한 학습 예제이지 임의 데이터 전체에 적용할 일반 해법이 아닙니다.

↳ Oracle WITH TIES의 동점은 전체 ORDER BY 키를 비교

아래 Oracle 비교 SQL에서 ORDER BY exam_score DESC NULLS LAST FETCH FIRST 2 ROWS WITH TIES는 95점 S106과 90점 S101·S103 총 3행을 포함할 것으로 예상됩니다(90점끼리 표시 순서는 미보장). 같은 구문에 student_id ASC를 추가하면 정렬 키 조합이 유일해져 S106·S101 총 2행만 남습니다. 이는 SQLD용 예상 결과이며 Oracle 실서버에서 직접 실행한 검증 결과가 아닙니다.

10

10. GROUP BY 결과도 다시 정렬해야 하나요?

06P에서 GROUP BY department_id로 그룹을 만들었습니다. 하지만 GROUP BY 자체는 결과의 표시 순서를 보장하지 않아요. COUNT(*) AS student_count로 그룹별 인원을 구했다면 ORDER BY student_count DESC를 붙여 인원이 많은 그룹부터 표시할 수 있습니다.

↳ WHERE·GROUP BY·HAVING·ORDER BY 연결

06O의 WHERE는 행을 먼저 걸러 주고, 06P의 GROUP BY·HAVING은 그룹을 만들어 골라 내며, 이번 ORDER BY는 최종 결과 행의 표시 순서를 정합니다. 이는 논리적으로 결과를 이해하기 위한 순서이지 DBMS의 물리적 실행 계획을 고정하는 뜻이 아닙니다.

! SUM·COUNT 별칭으로 정렬할 때 동점 주의

G3에서는 두 학과 모두 2명이므로 ORDER BY student_count DESC만으로는 D10·D20의 상대적 순서가 보장되지 않습니다. department_id ASC를 추가해 결과를 확정했습니다.

11

11. 전체 SQL을 복사해 직접 결과를 확인해요

앞의 정렬 예제 30개를 새 빈 SQLite 3.30 이상 데이터베이스에 테이블 생성·데이터 삽입부터 독립 실행해 볼 수 있어요. 각 SQL의 SELECT 열 이름·결과 행 수·모든 행의 순서를 사전 검증했습니다. NULL이라고 표시한 셀은 실제 데이터베이스의 SQL NULL을 읽기 쉽게 적은 것입니다.

↳ 데이터 원본과 실습의 독립성

06P의 S101~S106 기본 데이터는 동일하며 exam_score만 이 단원에서 추가했습니다. GROUP BY·WHERE·ORDER BY를 결합할 때에도 가상 데이터 외의 실제 수험생 정보를 사용하지 않습니다. SQLite 결과는 직접 검증했지만 Oracle·PostgreSQL 서버 직접 실행은 미확인입니다.

12

12. ORDER BY 절 핵심 요약

  • ORDER BY 없는 결과 행 순서는 보장되지 않습니다. INSERT 순서와 혼동하지 마세요.
  • ASC가 기본 오름차순, DESC가 내림차순입니다. ASC/DESC는 각 키마다 독립적으로 적용돼요.
  • 여러 키는 왼쪽부터 우선순위를 가집니다. 모든 정렬 키가 동점이면 순서 보장이 없습니다.
  • 열 이름·SELECT 별칭·출력 위치 번호로 정렬할 수 있지만, 번호는 SELECT 열 위치 기준이에요.
  • SQLite의 기본 NULL: ASC 앞, DESC 뒤. Oracle·PostgreSQL은 기본적으로 반대입니다.
  • NULLS FIRST/LAST를 지원하는 DBMS에서는 명시하고, 필요하면 CASE로 NULL 위치를 먼저 정합니다.
  • Top N은 정렬한 후 행 수 제한: SQLite의 LIMIT, Oracle의 FETCH FIRST 등 제품별 문법을 구분하세요.
  • LIMIT은 동점도 행 수로 자르지만, WITH TIES는 최종 정렬 경계 동점 포함이라는 별도의 요구입니다.
  • GROUP BY와 ORDER BY는 다른 역할: 그룹을 만드는 것과 그룹 결과를 정렬하는 것은 구별합니다.
↳ 이전·다음 단원
