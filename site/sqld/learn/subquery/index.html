안쪽 SQL의 답을 바깥에서 사용할까요? 서브쿼리

06R·06S에서는 JOIN으로 여러 테이블을 연결했어요. 이제는 SQL 안에 다른 SELECT를 넣어 먼저 찾은 값을 조건에 사용하거나, 결과표를 만들어 다음 SQL에 전달해 보겠습니다.

서브쿼리는 반환 모양과 사용 위치가 중요해요. IN은 목록 비교, EXISTS는 행 존재 여부, 스칼라는 한 값, 인라인 뷰는 FROM의 결과표입니다. 연관 서브쿼리는 바깥 열을 참조하고, NOT IN은 NULL을 주의해야 합니다. SQLite 실습 문법과 Oracle/PostgreSQL 문법 차이도 구별하세요.

이 단원을 끝내면

  1. 1안쪽 SELECT가 반환한 값을 바깥 SELECT의 조건에 연결해 설명할 수 있어요.
  2. 2단일행·다중행·다중열 서브쿼리의 행·열 수와 연산자 적합성을 판별해요.
  3. 3IN·ANY·ALL·EXISTS의 의미를 구분하고 비NULL 예제의 결과를 예측해요.
  4. 4연관과 비연관 서브쿼리를 외부 열 참조로 구별해요.
  5. 5SELECT 절 스칼라와 빈 결과의 NULL, COUNT 집계의 0을 구별해요.
  6. 6FROM 인라인 뷰의 결과표와 바깥 SELECT의 역할을 구분해요.
  7. 7NOT IN·NOT EXISTS와 NULL·빈집합의 차이를 설명해요.
  8. 8실제 SQL에서 안쪽 결과→외부 필터→최종 출력 흐름을 추적해요.
학습 기록을 불러오는 중이에요.

02

02. 괄호 속 SELECT 결과가 어디에 쓰일까요?

서브쿼리는 SQL 문 안에 포함된 SELECT예요. 이번 실습에서는 WHERE의 비교값이나 IN의 값 목록, SELECT의 출력 값, FROM의 임시 결과표로 사용합니다. 내부 SQL이 두 단계로 중첩될 수도 있습니다.

↳ 안쪽 → 결과 → 바깥

A1에서 내부 쿼리의 출력은 D10, A2에서는 그 값을 학생 표에 적용해 S101·S103·S106을 찾습니다. A3는 강좌 이름 → 강좌 코드 → 수강 학생 ID → 학생으로 이어지는 2단계 중첩입니다.

! 모든 서브쿼리를 같은 방향으로 계산하지는 않습니다

외부 행의 값을 참조하는 연관 서브쿼리는 바깥 행에 따라 안쪽의 조건이 달라집니다. 뒤의 05절에서 따로 배워요.

03

03. 결과가 한 개일까요, 여러 행·여러 열일까요?

서브쿼리는 행 수와 열 수를 나누어 봐야 해요. 한 행 한 열은 스칼라 비교값이 될 수 있고, 여러 행 한 열은 IN처럼 집합 조건에 쓰며, 두 열 이상이면 같은 개수의 왼쪽 열과 짝지어 비교할 수 있습니다.

형태별 읽는 법
안쪽 결과 모양맞는 사용 예이번 예제
1행 × 1열study_hours > (SELECT AVG(...))B1: 평균 7.5
여러 행 × 1열department_id IN (SELECT ...)B2: D10·D20
여러 행 × 2열(department_id, exam_score) IN (SELECT 열1, 열2 ...)B3: (D10,90)·(D20,80)
↳ 다중열은 열마다 따로 비교하는 게 아니에요

B3에서 (D10,90)과 (D20,80)이라는 행값 두 개를 비교합니다. 서로 다른 행에서 가져온 D10과 80을 하나의 짝으로 만들지 않아요.

! DBMS별 단일행 위반 차이

B5는 SQLite 전용 관찰 예제입니다. SQLite에서 스칼라 서브쿼리에 여러 행이 반환되면 첫 행 값이 사용되지만, Oracle의 단일행 비교에서는 ORA-01427 오류가 납니다. 안전한 SQL은 단일행을 보장하거나 여러 행에 알맞은 연산자를 사용합니다. SQLite의 첫 행 선택을 다른 DBMS의 정답으로 일반화하지 마세요.

04

04. 하나라도 맞으면 IN·ANY, 모두 맞으면 ALL?

IN은 오른쪽 서브쿼리의 값 중 같은 값이 하나라도 있으면 참이고, EXISTS는 안쪽에 행이 하나라도 존재하면 참이에요. Oracle·PostgreSQL의 > ANY는 어느 값 하나보다 큰지, > ALL은 모든 값보다 큰지를 묻습니다.

비NULL 집합 {80, 90}을 비교한 결과
왼쪽 점수> ANY (80,90)> ALL (80,90)
80FALSEFALSE
90TRUE (80보다 큼)FALSE (90보다 크지 않음)
95TRUETRUE
↳ SQLite 실습에는 EXISTS로 뜻을 비교했어요

SQLite 일반 SQL에는 > ANY (SELECT ...), > ALL (SELECT ...)를 그대로 실행할 수 없습니다. C4는 NULL 없는 비어 있지 않은 80·90 집합에 대한 > ANY 대응 EXISTS, C5는 같은 제한을 둔 > ALL 대응 NOT EXISTS입니다. Oracle·PostgreSQL 문법 자체를 SQLite에서 실행 검증했다고 주장하지 않아요.

↳ 존재 여부와 반환 셀의 내용은 별개

C6에서는 EXISTS (SELECT NULL ...)처럼 안쪽 셀에 NULL만 있어도 행이 한 개 이상이면 TRUE(1)입니다. C7의 S105처럼 안쪽에 0행이면 FALSE(0)예요.

! 빈 집합과 NULL까지 생각하면 단순 변환식은 달라집니다

빈 집합에서 ANY는 FALSE, ALL은 TRUE예요. 비교가 UNKNOWN인 행이 있으면 ANY는 TRUE가 없을 때, ALL은 FALSE가 없을 때 UNKNOWN이 됩니다. C4/C5의 SQLite 대응 실습은 NULL 없는 비어 있지 않은 {80, 90}에 한정합니다.

06. SELECT 옆에 학과 이름 한 칸을 붙일 수 있나요?

스칼라 서브쿼리는 필요한 위치에서 한 값을 제공하는 서브쿼리예요. 이번에는 학생 ID 옆에 학과 이름, 학생별 수강 건수, 전체 평균을 각각 한 칸씩 표시해 보겠습니다.

값이 없을 때 어떤 결과가 나올까요?

07

07. FROM 안쪽에서 작은 결과표를 먼저 만들어요

FROM (SELECT ...) v에서 괄호 안은 인라인 뷰(derived table)로 생각할 수 있습니다. F1에서 학생을 학과별로 모아 student_count가 있는 결과표를 만든 뒤, 바깥 쿼리가 인원 2명 이상 학과를 선택합니다.

↳ 이름 붙이기와 출력 열

안쪽의 집계 열 COUNT(*) AS student_count는 바깥에서 v.student_count로 읽어요. 인라인 뷰 v처럼 별칭을 명확히 지정해 어떤 결과를 재사용하는지 보여 주세요.

! 정렬 순서·LIMIT 이식성

인라인 뷰 내부의 ORDER BY는 바깥 반환 순서를 보장하지 않아요. F4의 SQLite 실습에서는 내부 ORDER BY와 LIMIT 2로 대상을 고르고 바깥 ORDER BY로 출력 순서를 지정합니다. PostgreSQL도 LIMIT을 지원하며 Oracle에서는 FETCH FIRST 2 ROWS ONLY를 사용할 수 있어요. 두 DBMS는 점수 DESC에서 기본적으로 NULL이 먼저 와서 S105가 상위에 들어갈 수 있어요. 점수 NULL을 뒤로 보낼 때는 안쪽 정렬에 DESC NULLS LAST를 명시하세요. 두 DBMS는 문서로 확인했으며 실서버에서는 실행하지 않았습니다.

08

08. NOT IN인데 왜 D30이 안 나올까요?

“학생이 한 명도 속하지 않은 학과”는 D30입니다. 그런데 NOT IN (SELECT department_id FROM study_students)를 그대로 쓰면 학생 S105의 SQL NULL 때문에 D30도 나오지 않습니다. NULL은 문자열이나 0이 아니라 “알 수 없는 값”이에요.

학과가 학생 목록에 없는지 비교
학과NOT IN (NULL 포함)NOT EXISTS
D10FALSE(0)FALSE(0)
D20FALSE(0)FALSE(0)
D30UNKNOWN(NULL)TRUE(1)
↳ G2의 NOT NULL 전제와 G3의 비교 조건

G2는 왼쪽 학과 테이블의 d.department_id가 NOT NULL이고, 오른쪽 학생의 학과 코드에서 NULL을 제외해 NOT IN으로 D30을 찾습니다. G3의 NOT EXISTS는 s.department_id = d.department_id가 TRUE인 학생 행이 있는지 확인해요. D30과 일치하는 행이 없어서 TRUE입니다. 두 예제 모두 D30 한 행을 반환해요.

! 왼쪽 NULL과 빈 집합은 따로 확인해요

단일 학과 코드 비교에서는 오른쪽에서 NULL을 모두 제외해도, 남은 행이 있고 왼쪽 값이 SQL NULL이면 NOT IN은 UNKNOWN이에요. 예를 들어 S105의 NULL 학과 코드를 {D10, D20}과 비교하는 경우예요. G6처럼 오른쪽이 0행인 빈 집합이면 왼쪽이 NULL이어도 NOT IN은 TRUE(1)입니다. 같은 왼쪽 NULL을 NOT EXISTS에서 등호로 비교하면 조건이 TRUE인 행이 없어 TRUE예요. 일치 여부는 서브쿼리에 적은 조건에 따라 달라집니다.

09. 중첩·연관·인라인 뷰를 함께 읽어요

복잡한 SQL을 보면 먼저 서브쿼리가 어떤 열과 몇 행을 반환하는지 찾고, 바깥에서 IN·EXISTS·> 또는 FROM의 별칭으로 어떻게 사용하는지 확인하세요. 서로 다른 위치에 서브쿼리가 두 개 이상 있어도 이 원칙은 같습니다.

↳ H1의 중첩 경로

강좌명=SQL 입문 → 강좌 C01 → 수강 ID에서 학생 S101·S102·S104·S106 → 외부 학생 네 행의 결과입니다. 같은 학생이 수강 여러 건을 가져도 IN의 바깥 학생은 한 번씩 나오죠.

↳ H6은 연관 조건 두 개를 함께 검사

학생 자신의 학과 평균보다 시간이 길고, 수강 행이 적어도 하나 존재해야 합니다. 두 조건을 모두 통과하는 S103·S104·S106이 나옵니다.

! 최종 결과만 암기하지 마세요

학생 수·등록 수·중복 여부와 NULL 처리, 바깥 ORDER BY를 확인하세요. 다른 데이터로 바뀌면 결과 행 수도 달라집니다.

12. 서브쿼리 핵심을 정리해요

  • 서브쿼리는 SQL 문 안에 포함된 SELECT로, 바깥 SQL에 값·목록·결과표를 제공해요.
  • 단일행/다중행/다중열은 행 수와 열 수를 나누어 구분해요.
  • IN은 값 일치 여부, EXISTS는 안쪽 행 존재 여부를 판단해요.
  • ANY는 하나라도, ALL은 모두의 조건이며 빈집합과 NULL에서는 예외 의미를 주의해요.
  • 연관 서브쿼리는 외부 쿼리의 열을 참조하고, 비연관 서브쿼리는 참조하지 않아요.
  • 스칼라 서브쿼리의 0행 반환은 NULL, COUNT 집계의 0행 입력 결과는 0일 수 있어요.
  • FROM 서브쿼리는 인라인 뷰가 되며 바깥에서 열·정렬을 선택해요.
  • NOT IN의 내부 NULL은 D30 같은 미일치 값을 UNKNOWN으로 만들 수 있어 NOT EXISTS와 구분해요.
↳ 핵심 암기보다 추적

서브쿼리 위치 → 반환 모양 → 비교 방식 → 연관 열 → NULL → 바깥 결과 순서로 결과를 설명하세요.
