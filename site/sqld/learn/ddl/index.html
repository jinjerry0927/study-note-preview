DDLData Definition Language

개념부터 차근차근!

테이블과 규칙은 어떻게 만들까요? DDL

06AB에서는 행을 INSERT·UPDATE·DELETE했고, 06AC에서는 변경을 COMMIT·ROLLBACK했습니다. 06AD에서는 그 행을 담는 테이블의 구조와 규칙을 만들고 바꾸는 DDL을 배웁니다.

DDL은 데이터베이스 객체의 정의를 다룹니다. CREATE로 테이블·제약을 만들고 ALTER·RENAME으로 구조를 바꾸며 DROP으로 객체를 제거합니다. DELETE·TRUNCATE·DROP의 대상과 DBMS별 트랜잭션 규칙은 다르므로 문맥을 확인하세요.

이 단원을 끝내면

  1. 1DDL과 DML의 역할, CREATE·ALTER·DROP의 적용 대상을 구별해요.
  2. 2CREATE TABLE의 열 정의·자료형·DEFAULT를 이해하고 실제 SQL 결과를 확인해요.
  3. 3PRIMARY KEY, UNIQUE, NOT NULL, CHECK의 제약과 NULL 처리 경계를 비교해요.
  4. 4FOREIGN KEY와 ON DELETE CASCADE·SET NULL·RESTRICT 동작을 표로 계산해요.
  5. 5ALTER TABLE의 열 추가·이름 변경·삭제와 제약 때문에 실패하는 예제를 설명해요.
  6. 6DELETE·TRUNCATE·DROP의 행·테이블 정의 차이를 구분해요.
  7. 7Oracle의 DDL 암묵적 COMMIT과 SQLite·PostgreSQL·SQL Server의 관련 차이를 분리해 설명해요.
  8. 8총 40개 SQLite 사례 중 올바른 결과와 예상 오류를 찾아낼 수 있어요.
학습 기록을 불러오는 중이에요.
01

01. 데이터를 담을 표부터 만들어야 할까요?

앞 단원 06AB DML은 학생 표에 행을 추가·수정·삭제하는 작업이었어요. 그런데 그 학생 표의 이름과 열, 반드시 지켜야 할 규칙은 누가 정할까요? 그 구조를 만드는 언어가 DDL(Data Definition Language, 데이터 정의어)입니다.

DDL과 DML의 역할
분류대표 명령주로 바꾸는 대상
DDLCREATE · ALTER · DROP · TRUNCATE · RENAME테이블 등 데이터베이스 객체의 정의·구조(명령별 차이 있음)
DMLINSERT · UPDATE · DELETE테이블 안의 데이터 행
조회SELECT저장된 데이터에서 결과를 반환(분류 방식은 교재마다 다를 수 있음)

교실을 예로 들면, 교실 설계도(DDL)를 정하고 그 안에 학생 명단(DML)을 넣습니다. 설계도에는 학번과 이름의 열, 학번 중복 금지, 소속 학과 존재 여부 같은 규칙을 적을 수 있어요.

↳ A1·A3·A4

SQLite의 sqlite_schema에 테이블·뷰·인덱스의 정의를 조회합니다. 뷰와 인덱스는 개념 보조 사례이고, 핵심 학습은 테이블·제약·변경·삭제입니다.

! 명령 이름만으로 트랜잭션 처리까지 단정하지 마세요

DDL의 암묵적 COMMIT은 DBMS마다 다릅니다. Oracle과 SQLite의 차이는 09절에서 별도로 설명합니다.

02

02. CREATE TABLE로 표의 설계도를 써요

CREATE TABLE은 테이블 이름과 각 열의 이름·자료형·선택적인 제약을 지정합니다. 06AD의 학생 데이터는 학생 ID, 이름, 학과 코드, 점수, 이메일, 재학 상태로 구성했습니다.

기준 학생 4명의 원본 데이터
student_idstudent_namedept_idscoreemailstatus
S101민지D1090minji@example.com재학
S102준호D2080junho@example.com재학
S103서연D10SQL NULLSQL NULL재학
S104지훈SQL NULL75SQL NULL재학

대표 SQL(SQLite 실습) CREATE TABLE classrooms (room_id TEXT PRIMARY KEY, capacity INTEGER CHECK(capacity>0)); → room_id라는 식별자와 양수 정원을 가진 교실 표를 만듭니다. 원래 학생 4명은 변하지 않아요(A2).

↳ A5 — IF NOT EXISTS

CREATE TABLE IF NOT EXISTS departments (...)는 같은 이름의 테이블이 있으면 새 정의로 덮어쓰지 않습니다. 기존 열을 그대로 유지합니다.

↳ B5 — CTAS의 제약 복사 금지

SQLite의 CREATE TABLE students_copy AS SELECT ... FROM students는 데이터를 복사하지만 원본 PK·UNIQUE 등의 제약을 자동 복사하지 않습니다. SQLD 표준 CREATE TABLE과 혼동하지 마세요.

! CREATE VIEW는 일반 테이블의 물리적 복사와 다릅니다

뷰는 저장된 SELECT 정의입니다. 일반적인 뷰를 만드는 것만으로 결과 행을 별도 테이블에 복제한다고 생각하면 안 됩니다.

03

03. 데이터 타입과 DEFAULT는 어떻게 해석할까요?

자료형은 열에 어떤 종류의 값을 저장할지 선언합니다. Oracle에서는 VARCHAR2, NUMBER, DATE 등이 흔하고, SQL Server에는 VARCHAR, INT, DATETIME2 등이 있습니다. 실습 SQLite의 `TEXT`, `INTEGER`, `REAL`과 의미나 검증 강도를 그대로 동일시하면 안 됩니다.

기초 자료형 대비 — 개념 수준
용도Oracle 예SQLite 실습
문자VARCHAR2(30)TEXT
정수·숫자NUMBER(3), NUMBER(6,2)INTEGER, REAL
날짜·시각DATE, TIMESTAMP일반적으로 TEXT/INTEGER/REAL 등의 저장 형식 사용

DEFAULT는 값을 지정하지 않은 경우에 적용할 초기값입니다. B3에서 flag 열을 생략한 행은 신규가 되고, flag=NULL을 명시한 행은 실제 SQL NULL로 남습니다.

B3 — 기본값과 명시적 NULL
idflag왜?
1신규INSERT에서 flag 생략
2SQL NULLINSERT에서 flag=NULL 명시
↳ B1·B2 — 선언과 실제 저장은 다릅니다

SQLite에서는 VARCHAR(2)로 선언해도 ABCDE 5글자가 저장됩니다. Oracle의 VARCHAR2 길이 제한 예제에 이 SQLite 결과를 적용하지 마세요.

! NULL과 문자열 NULL, 길이 제한을 혼동하지 마세요

NULL은 값이 없음을 나타내는 SQL NULL입니다. 문자열 'NULL'과 다르며, 타입·길이 검증은 DBMS와 열 정의에 따라 달라집니다.

04

04. PRIMARY KEY·UNIQUE·NOT NULL·CHECK

테이블을 만들면서 데이터가 지켜야 할 규칙을 정의할 수 있습니다. PRIMARY KEY는 행 식별에 사용하는 유일하고 비어 있지 않은 키, UNIQUE는 값의 중복 제한, NOT NULL은 NULL 금지, CHECK는 지정한 조건에 맞는지 검사합니다.

학생 테이블의 제약 사례
제약예시실습 결과
PRIMARY KEYstudent_id TEXT NOT NULL PRIMARY KEYS101 중복 INSERT 실패(C1)
NOT NULLstudent_name TEXT NOT NULL필수 이름 누락 금지
UNIQUEemail TEXT UNIQUE같은 비NULL 이메일 중복 실패(C3)
CHECKscore BETWEEN 0 AND 100150은 실패(C5), NULL은 허용
DEFAULTstatus DEFAULT '재학'INSERT 열 생략 시 재학 값
↳ C4 — UNIQUE와 여러 NULL

SQLite의 UNIQUE(email)에는 SQL NULL인 행이 여러 개 존재할 수 있습니다. 원래 두 행에 S105를 추가하면 NULL 이메일은 3행입니다.

↳ C5 — CHECK에서 UNKNOWN

SQLite CHECK식의 결과가 0(FALSE)일 때 위반이며, NULL(UNKNOWN)은 위반이 아닙니다. NULL 자체를 금지하려면 NOT NULL과 함께 설계해야 합니다.

! SQLite TEXT PRIMARY KEY에는 중요한 예외가 있습니다

일반 SQLite 행 테이블에서 TEXT PRIMARY KEY만 쓰면 역사적 호환성 때문에 NULL을 허용할 수 있습니다. 본 학습 데이터에는 TEXT NOT NULL PRIMARY KEY로 명시했습니다. ‘기본 PK는 NULL 불가’라는 SQL 원칙과 SQLite의 예외를 나누어 이해하세요.

05

05. FOREIGN KEY는 부모 표와 자식 표를 연결해요

FOREIGN KEY(자식의 학과 코드) REFERENCES departments(부모의 학과 코드)는 자식이 없는 부모 번호를 함부로 가리키지 못하게 합니다. 그래서 D99 학과가 없을 때 학생을 D99로 추가하면 실패합니다(D1).

부모 삭제 시 자식에 대한 동작
설정부모 삭제 시실습
기본 NO ACTION(시점은 제약 설정 영향)참조를 어기면 삭제 거부기본 FK
ON DELETE CASCADE참조하는 자식 행도 삭제D3: M1·M2 삭제, M3 유지
ON DELETE SET NULL참조하는 자식의 FK만 NULL로 변경D4: R1 남고 team_id=NULL
ON DELETE RESTRICT자식이 있으면 부모 삭제 제한D5: L1 삭제 실패
↳ D2 — 부모를 먼저 만들면

학과 D30을 INSERT한 뒤 그 학과를 참조하는 학생 S105를 넣으면 성공합니다. 학과의 부재/존재가 결과를 결정합니다.

! SQLite 실습은 PRAGMA foreign_keys=ON이 필요합니다

각 독립 DB에서 실행 전에 PRAGMA foreign_keys=ON을 명시했습니다. SQLite의 기본 FK 활성화 여부에 의존하지 마세요. 그리고 ON DELETE CASCADE와 DROP TABLE ... CASCADE는 다른 문맥의 CASCADE입니다.

! SET NULL에는 NULL 가능한 자식 열이 필요합니다

자식 FK 열이 NOT NULL이면 삭제 동작이 SET NULL을 시도할 때 제약 충돌이 납니다. 이번 D4는 자식 열을 NULL 허용으로 선언했습니다.

06

06. ALTER TABLE로 기존 표를 바꿔요

ALTER TABLE은 이미 존재하는 테이블의 구조를 변경합니다. 가능한 변경의 종류와 문법은 DBMS마다 다르므로, SQLite의 ADD COLUMN·RENAME COLUMN·DROP COLUMN을 Oracle의 MODIFY/DROP 문법과 혼동하지 마세요.

06AD 실습에서 검증한 변경
코드변경결과
E1ADD COLUMN grade TEXT NOT NULL DEFAULT '기본'기존 4행에서 grade=기본
E2RENAME COLUMN student_name TO full_name이름만 변경, 값 유지
E3RENAME TO learners학생 4행 유지·옛 테이블명 제거
E4ADD COLUMN nickname 후 DROP COLUMN nickname제약 없는 열 삭제
E5ADD COLUMN badge TEXT NOT NULL (기본값 없음)기존 행 때문에 오류
↳ 왜 기본값을 함께 쓰나요?

기존 행이 있는 테이블에 NOT NULL 열을 추가하면 과거 행을 채울 값이 필요합니다. SQLite E5는 기본값 없이 추가하려다 실패합니다.

! ALTER로 가능한 작업은 DBMS마다 다릅니다

SQLite는 ALTER TABLE ... ADD CONSTRAINT 등 많은 형태를 직접 지원하지 않습니다. 필요한 경우 테이블 재구성 등이 요구되며, 그런 작업은 이 단원 실습 범위 밖입니다.

07

07. DELETE·TRUNCATE·DROP은 무엇을 지울까요?

세 명령은 결과가 비슷해 보여도 대상이 다릅니다. DELETE는 행을 삭제하는 DML, TRUNCATE TABLE은 모든 행을 비우는 테이블 관련 DDL 성격의 명령(지원 DBMS에서), DROP TABLE은 테이블 정의 자체를 제거합니다.

대상과 문법을 구분
명령행 데이터테이블 정의WHERESQLite 실습
DELETE FROM students제거(WHERE 조건 가능)유지가능F1: 4→0행, 표 남음
TRUNCATE TABLE students모든 행 제거(지원 DBMS)유지불가능F3: 구문 오류(지원 안 함)
DROP TABLE students행과 테이블 제거제거불가능F2: 표 자체 사라짐

트랜잭션의 취소 가능 여부는 DBMS별로 다릅니다. Oracle은 DDL의 암묵적 COMMIT이 중요합니다. PostgreSQL과 SQL Server는 명시적 트랜잭션 안의 TRUNCATE를 롤백할 수 있습니다. SQLite는 TRUNCATE 자체를 지원하지 않습니다.

↳ F3 — 실패도 학습 결과입니다

TRUNCATE TABLE students를 SQLite에서 실행하면 SQL 구문 오류가 발생하며, 이 실습의 학생 수는 그대로 4명입니다. DELETE FROM students를 TRUNCATE와 동등한 DBMS 기능으로 표시하지 않았습니다.

! TRUNCATE가 언제나 ROLLBACK 불가능하다는 말은 틀립니다

SQL Server와 PostgreSQL의 공식 문서는 트랜잭션 안에서 TRUNCATE를 취소할 수 있다고 설명합니다. DBMS를 확인하지 않고 일률적으로 “TRUNCATE는 절대 복구 불가”로 외우지 마세요.

! DROP TABLE은 조회 대상이 없어집니다

DROP 이후 같은 이름으로 SELECT하려면 새 객체를 만들거나 트랜잭션 롤백처럼 DBMS가 지원하는 복구 절차가 필요합니다.

08

08. RENAME은 이름뿐 아니라 참조를 살펴봐요

테이블명이나 열명을 바꾸는 작업은 식별자를 바꾸는 DDL입니다. 다른 제약·뷰가 그 이름을 참조하고 있다면 영향이 있으므로 실제 의존 관계까지 살펴야 합니다.

변경 후 참조 확인
코드명령확인 결과
G1ALTER TABLE departments RENAME TO facultiesstudents FK 참조 부모가 faculties로 갱신
G2ALTER TABLE departments RENAME COLUMN dept_id TO dept_codestudents FK가 참조하는 부모 열명 갱신
G3ALTER TABLE students RENAME COLUMN student_name TO full_name관련 VIEW SQL도 갱신
G4ALTER TABLE students RENAME TO departments이미 이름이 존재하므로 실패
G5ALTER TABLE students RENAME TO learnersVIEW가 새 테이블명을 참조
↳ SQLite 버전 기준

위 의존 정의의 자동 수정은 SQLite 3.46.1의 실제 실행 결과입니다. 다른 DBMS에서는 제약·뷰·권한·객체 종류에 따라 동작이 달라집니다.

! RENAME만 했다고 모든 응용 코드가 자동 수정되는 것은 아닙니다

DB 내부 정의의 갱신과 웹 앱 SQL 문자열·외부 프로그램 수정은 별개의 문제입니다. 운영 환경에서는 영향 범위 점검이 필요합니다.

09. DDL을 실행하면 COMMIT이 자동으로 될까요?

앞 단원 TCL과 연결되는 핵심입니다. Oracle 19c는 DDL 앞뒤에 암묵적 COMMIT 규칙이 있습니다. 반면 SQLite에서는 명시적 BEGIN 안의 CREATE·ALTER·DROP을 ROLLBACK할 수 있습니다. PostgreSQL에서도 많은 DDL을 트랜잭션 안에서 관리할 수 있지만, 지원 여부는 명령별 확인이 필요합니다.

DDL/트랜잭션 차이 — 반드시 DBMS를 확인
DBMS행동상태

↳ H3·H5도 직접 실행

SQLite는 트랜잭션 안에서 DROP TABLE 한 뒤 ROLLBACK으로 복원(H3)할 수 있고, DROP INDEX 뒤 ROLLBACK하여 인덱스를 복원(H5)할 수도 있습니다.

! Oracle의 DDL COMMIT 규칙은 성공 여부·문법 오류의 세부 사례를 구분해야 합니다

Oracle 공식 문서의 “DDL 앞 암묵적 COMMIT”을 기초로 설명합니다. 모든 종류의 실패한 구문에서 동일한 부작용이 난다고 단정하지 않고 실제 서버와 명령 종류 확인이 필요합니다.

12. DDL 핵심 요약

  • CREATE TABLE: 표의 열·타입·제약 등 구조를 정의합니다.
  • PRIMARY KEY: 행을 구별하는 유일한 키. 일반 SQL 원칙은 NOT NULL이며 SQLite TEXT PK 예외를 주의합니다.
  • UNIQUE: 비NULL 값의 중복을 제한합니다. SQLite에서 SQL NULL은 여러 행이 가능합니다.
  • NOT NULL / CHECK / DEFAULT: NULL 금지 / 조건 검사 / 입력 생략 시 기본값을 구분하세요.
  • FOREIGN KEY: 부모 키를 참조합니다. ON DELETE CASCADE와 SET NULL은 동작이 다릅니다.
  • ALTER / RENAME: 테이블 구조·이름을 바꿉니다. 참조되는 객체를 함께 확인하세요.
  • DELETE는 행, TRUNCATE는 전체 행(지원 DBMS), DROP은 테이블 정의까지 제거합니다.
  • DDL의 트랜잭션: Oracle 19c의 암묵적 COMMIT과 SQLite의 명시적 BEGIN 안 DDL 취소를 혼동하지 않습니다.
↳ 관련 단원

앞선 06AB DML, 06AC TCL에서 배운 행 변경·거래 제어와 이어집니다. 마지막 06AE DCL에서는 데이터베이스 사용 권한을 관리합니다.
