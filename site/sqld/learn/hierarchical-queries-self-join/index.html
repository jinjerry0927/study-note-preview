01. 한 표에서 조직도를 만들 수 있을까요?

학생 명단은 한 줄로 볼 수 있었지만, 회사 조직도는 대표 아래 본부, 본부 아래 팀, 팀 아래 파트가 있어요. 부모 한 사람과 바로 아래 자식 여러 명의 연결을 표에 적는 것이 계층 데이터의 출발입니다. 이번 단원에서는 같은 직원 표를 두 번 읽는 셀프 조인과, 여러 세대를 따라가는 계층형 질의를 구분합니다.

02

02. 같은 표를 두 번 읽는 셀프 조인

셀프 조인(self join)은 같은 테이블을 다른 역할로 두 번 참조하는 조인입니다. org_employees c는 아래쪽 자식, org_employees p는 바로 위 부모로 사용하고 c.parent_id = p.emp_id로 연결합니다. 테이블은 하나여도 별칭이 있어야 두 역할을 구별할 수 있습니다.

A1과 A2: 루트 포함 여부
구문결과이유
A1 LEFT JOIN11행부모가 없는 루트 E100·E200도 NULL 부모로 보존
A2 INNER JOIN9행연결 가능한 부모가 있는 노드만 반환
↳ A3에 주목

직속 자녀가 0명인 부모도 보존하고 싶다면 LEFT JOIN 후 COUNT(c.emp_id)를 쓰세요. 보존된 NULL 행을 COUNT(*)로 계산하면 1로 오해할 수 있습니다.

! 셀프 조인 ≠ 재귀 탐색

단일 셀프 조인은 보통 한 단계(직속 관계)를 구합니다. A5처럼 조인을 여러 번 연결하면 조부모 등 정해진 단계까지는 구할 수 있지만, 임의 깊이 전체 탐색에는 재귀가 편리합니다.

03

03. 부모·자식·루트·리프 노드

루트(root)는 지금 탐색하는 나무의 시작 노드, 자식(child)은 한 단계 아래 직접 연결된 노드, 후손(descendant)은 자식·손자 등을 모두 포함한 아래 노드, 리프(leaf)는 더 아래 연결할 자식이 없는 노드입니다. parent_id IS NULL은 이 예제의 전체 조직도 루트 E100과 E200을 찾는 조건입니다.

조직도의 노드 수
구분노드 ID개수
루트E100, E2002
E100 직속 자식E110, E1202
E110 하위(자신 포함)E110, E111, E112, E113, E1145
리프E112, E113, E114, E122, E2105
↳ 루트는 상대적일 수 있어요

조직도 전체에서는 E100이 루트지만 START WITH emp_id = E110처럼 시작점을 바꾸면 E110이 해당 결과 트리의 LEVEL 1 루트가 됩니다.

! 리프는 NULL과 달라요

리프는 parent_id IS NULL인 행이 아닙니다. 자신의 emp_id를 parent_id로 참조하는 자식이 없는 행입니다. 데이터 전체와 질의의 가지 조건에 따라 리프 판정 범위가 달라질 수 있습니다.

04

04. START WITH·CONNECT BY·PRIOR의 방향

Oracle의 `START WITH`는 시작 행을 고릅니다. `CONNECT BY`는 부모·자식 연결 조건이며, `PRIOR`는 바로 뒤 식을 현재 부모 행에서 평가합니다. 대표에서 하위로 내려갈 때는 CONNECT BY PRIOR emp_id = parent_id라고 적습니다. 부모의 emp_id와 자식의 parent_id를 비교하는 뜻입니다.

같은 데이터에서 탐색 방향 비교
조회기준예상 결과
C1 아래로START WITH E100 / PRIOR emp_id = parent_idE100 포함 대표 트리 9행
C4 위로START WITH E114 / PRIOR parent_id = emp_idE114→E111→E110→E100 (4행)
C3 독립 트리START WITH E200E200, E210 (2행)
↳ Oracle 원형 SQL은 별도 파일

06Y_ORACLE19C_EXAMPLES.sql의 C1/C4 원형 쿼리는 공식 문서 기반 예시이며 실제 Oracle 서버에서 아직 실행하지 않았습니다. SQLite 실습은 방향을 동일하게 설명하는 WITH RECURSIVE입니다.

! PRIOR 위치를 바꾸면 이동 방향이 달라집니다

PRIOR emp_id = parent_id와 emp_id = PRIOR parent_id는 같은 식의 단순 재배열이 아닙니다. 부모 역할로 보는 식이 바뀌므로 아래→위 또는 위→아래 탐색 결과가 달라집니다.

05

05. LEVEL·CONNECT_BY_ISLEAF로 깊이와 끝 찾기

Oracle 계층형 질의에서 `LEVEL`은 시작 행이 1, 그 자식이 2, 손자가 3입니다. `CONNECT_BY_ISLEAF`는 현재 CONNECT BY로 정의된 나무에서 더 확장할 자식이 없으면 1, 있으면 0입니다. 이 값은 NULL 여부가 아니라 연결 가능성입니다.

대표 E100을 루트로 선택했을 때
노드LEVEL원본 자식 존재
E100 대표1있음
E110 개발본부2있음
E111 플랫폼팀3있음
E114 인프라파트4없음
E112 데이터팀3없음
↳ SQLite 대응 값

D2는 NOT EXISTS로 전체 원본에서의 자식 유무를 구합니다. Oracle CONNECT_BY_ISLEAF의 실제 값은 CONNECT BY 가지 제한의 영향을 받으므로 동일한 결과를 보장하는 대체 함수가 아닙니다.

! LEVEL은 고정 높이가 아닙니다

D5처럼 루트를 E110으로 바꾸면 E111의 LEVEL은 3에서 2로 내려옵니다. 어떤 START WITH를 사용했는지를 먼저 확인하세요.

06

06. 루트 이름과 경로를 한눈에

Oracle `CONNECT_BY_ROOT emp_name`은 각 노드에서 시작 루트의 이름을 보여 줍니다. `SYS_CONNECT_BY_PATH(emp_name, '/')`는 루트부터 지금 노드까지의 이름을 /로 이어 줍니다. 두 기능은 직접 부모 이름 하나를 구하는 셀프 조인과 다릅니다.

07

07. ORDER SIBLINGS BY는 형제만 정렬해요

계층형 결과를 그냥 ORDER BY emp_name으로 정렬하면 조직도 순서가 뒤섞일 수 있습니다. Oracle `ORDER SIBLINGS BY sort_order`는 같은 부모 아래의 자녀 순서를 정하되 부모→자식 구조를 유지하려는 구문입니다.

F1·F2·F3의 의미 차이
사례조건기대 효과
F1sort_order ASC개발본부 다음 운영본부
F2sort_order DESC운영본부 다음 개발본부
F3전역 ORDER BY emp_name부모-자식 순서 유지 보장 없음
↳ 결정적 순서

같은 sort_order가 있을 때에는 emp_id를 보조 키로 붙였습니다. SQLite에서는 부모부터 누적한 sort_path를 최종 ORDER BY에 사용해 교육용 계층 순서를 만듭니다.

! SQL 문법을 섞지 마세요

ORDER SIBLINGS BY는 Oracle 전용 계층 구문이며 SQLite에서는 실행되지 않습니다. F1~F5는 서로 다른 SQLite 쿼리로 *표시 결과*를 재현합니다.

08

08. 데이터가 원을 그리면 어떻게 할까요?

정상 트리에는 한 노드가 자신의 후손을 통해 다시 조상이 되는 순환(cycle)이 없어야 합니다. 순환 예제는 조직도와 별도인 X1 → X2 → X3 → X1입니다. Oracle에서 일반 CONNECT BY는 순환을 만나면 오류가 날 수 있고, `CONNECT BY NOCYCLE`로 일부 경로를 계속 조회하며 순환 표식을 조사할 수 있습니다.

SQLite 방문 이력 예제
현재이미 방문한 노드다음 간선순환 위험
X1X1X2없음
X2X1,X2X3없음
X3X1,X2,X3X1있음
↳ Oracle의 CONNECT_BY_ISCYCLE 정의

Oracle CONNECT_BY_ISCYCLE은 현재 행에 이미 자기 조상인 자식이 존재하면 1을 반환합니다. NOCYCLE을 지정한 경우에만 사용할 수 있습니다. G3은 다음 노드가 visited에 존재하는지를 SQLite에서 직접 계산한 교육용 시뮬레이션이며 Oracle에서 실행해 얻은 값은 아닙니다.

! 상한만으로 안전하다고 단정하면 안 돼요

G4의 깊이 제한 2는 무한 반복을 피하는 안전장치일 뿐, 사이클 검출 자체는 아닙니다. 운영 시스템에서는 ID별 방문 이력, 데이터 제약, 방언별 CYCLE/NOCYCLE 규칙을 확인해야 합니다.

09

09. WITH RECURSIVE: 여러 세대를 반복 탐색

재귀 CTE는 앵커(anchor) SELECT로 시작 행을 만들고, 재귀 SELECT에서 직전 단계의 결과를 바탕으로 자식을 찾습니다. 자식이 더 없으면 종료합니다. SQLite에서는 WITH RECURSIVE ... UNION ALL ...을 사용할 수 있습니다. c.parent_id = w.emp_id가 지금 노드와 다음 노드의 연결 조건입니다.

H1의 논리적 단계
단계대표 예제에서 새로 발견하는 노드
앵커 LEVEL 1E100
확장 LEVEL 2E110, E120
확장 LEVEL 3E111, E112, E121
확장 LEVEL 4E113, E114, E122
이후더 이상 새 자식 없음
↳ Oracle과 재귀 CTE는 같은 문장이 아니에요

Oracle 19c의 CONNECT BY와 SQLite/PostgreSQL의 재귀 CTE는 유사한 계층 결과를 만들지만 PRIOR, LEVEL, 의사열, 형제 정렬, 순환 처리 방식은 DBMS별로 다릅니다.

! ORDER BY 없이 계층 출력 순서를 단정하지 마세요

재귀 CTE의 내부 처리 순서나 최종 반환 순서가 항상 선행순회라고 보장할 수는 없습니다. 실습은 명시적인 sort_path/depth 정렬로 결과표 순서를 고정합니다.

10

10. WHERE로 숨기는 것과 가지를 끊는 것은 달라요

Oracle 계층형 질의에서는 JOIN이 먼저 평가되고, CONNECT BY로 관계를 확장한 뒤, 나머지 WHERE 필터는 조건에 맞지 않는 행만 제거하며 그 후손을 자동으로 전부 제거하지 않습니다. 반면 CONNECT BY 자체에 조건을 걸어 자식 확장을 막으면 그 아래 가지는 생기지 않습니다.

SQLite H4/H5로 확인한 차이

↳ 왜 배우나요?

부서를 숨기는 요구와 부서 전체를 제외하는 요구는 다릅니다. 어느 단계에서 조건을 적용하는지에 따라 전체 인원 집계까지 달라집니다.

! 문법에 따른 논리 차이를 구분하세요

H4/H5는 SQLite의 분리된 재귀 CTE와 후처리 필터를 사용해 원리를 설명합니다. Oracle 조인 조건이나 중첩 쿼리 전체를 기계적으로 동일하다고 간주하지 마세요.

11. A1~H5 전체 결과를 재현해요

A(셀프 조인)·B(계층 구조)·C(PRIOR 방향)·D(LEVEL/리프)·E(루트/경로)·F(형제 정렬)·G(순환)·H(재귀/필터)의 8묶음에서 각각 5개씩 총 40개 SQLite 조회를 준비했어요. 버튼을 눌러 SQL과 입력/출력 행을 대조하고, 한 번에 재현하고 싶다면 06Y_SQLITE_HIERARCHY.sql을 비어 있는 SQLite 데이터베이스에 실행합니다.

↳ 검증 근거

06Y_SCENARIOS.json의 SQL과 06Y_EXPECTED_RESULTS.json의 실제 조회 결과는 Python SQLite 3.46.1에서 열 이름·순서, 값, NULL, 행 순서까지 대조됩니다. Oracle 원형 SQL은 별도 파일이며 SQLite에 직접 실행하지 않습니다.

12

12. 계층형 질의 핵심 요약

  • 셀프 조인: 같은 테이블을 자식·부모 별칭으로 참조해 직속 관계를 구합니다.
  • START WITH: 계층형 질의의 시작 행/루트를 지정합니다.
  • CONNECT BY PRIOR emp_id = parent_id: Oracle에서 부모 ID와 자식의 부모 ID를 비교해 아래로 내려갑니다.
  • LEVEL: 시작점 1, 그 자식 2. CONNECT_BY_ISLEAF는 현재 계층 정의의 끝 여부입니다.
  • CONNECT_BY_ROOT와 SYS_CONNECT_BY_PATH: 루트 값과 루트→현재 노드 경로를 표시합니다.
  • ORDER SIBLINGS BY: 계층을 깨뜨리지 않고 형제 사이의 순서를 지정합니다.
  • NOCYCLE 및 CONNECT_BY_ISCYCLE: 순환이 있는 계층의 탐색과 순환 표시를 지원합니다.
  • WITH RECURSIVE: 앵커와 반복 SELECT로 여러 단계를 탐색하며 방문 이력·정렬을 명시해야 합니다.
↳ 시험에서 먼저 확인할 순서

① 루트 ② PRIOR 방향 ③ 탐색 깊이 ④ 리프/루트/경로 ⑤ 정렬과 순환 ⑥ WHERE와 가지 제한 차이. 실제 출제 빈도가 검증되었다는 뜻은 아닙니다.
