데이터 모델의 이해Understanding Data Models

개념부터 차근차근!

학교 정보를 저장하기 전에 설계도가 필요할까요?

학생·강좌·신청 기록을 아무 규칙 없이 쌓으면 찾기도 어렵고 수정할 때 헷갈릴 수 있어요. 정보를 담는 설계도부터 그리는 방법을 함께 배워 봐요.

데이터 모델링은 정보를 저장하기 전에 무엇을 관리하고 어떻게 연결할지 정하는 설계예요.

이 단원을 끝내면

  1. 1데이터 모델링을 하는 이유와 추상화·단순화·명확성의 차이를 쉽게 말할 수 있어요.
  2. 2데이터 관점·프로세스 관점·상관 관점을 학교 사례에서 구분할 수 있어요.
  3. 3개념적·논리적·물리적 모델링을 적절한 순서로 설명할 수 있어요.
  4. 4외부·개념·내부 스키마와 논리적·물리적 데이터 독립성을 구분할 수 있어요.
  5. 5좋은 모델의 유의사항과 ERD의 역할·기본 작성 순서를 설명할 수 있어요.
학습 기록을 불러오는 중이에요.
01

01. 왜 데이터 모델링이 필요할까요?

학교에 학생, 강좌, 수강신청 기록이 잔뜩 쌓였다고 상상해 봐요. 학생 이름 옆에 수업 이름을 적고, 수업 종이에도 학생 이름을 다시 적으면 같은 정보가 여기저기 흩어져요. 누가 어느 수업을 듣는지 확인하려면 한 장씩 뒤져야 하겠죠?

그래서 컴퓨터에 데이터를 넣기 전에 무엇을 관리할지, 각 정보가 어떻게 연결되는지, 어떤 규칙을 지켜야 하는지 먼저 약속해요. 이것이 데이터 모델링이에요.

↳ 정확한 정의

데이터 모델링은 업무에서 필요한 데이터의 의미·구조·관계를 분석하고, 일정한 방식으로 표현하는 설계 활동이에요. 데이터베이스를 만드는 일과 연결되지만, 단순히 SQL을 입력하거나 예쁜 그림을 그리는 일만을 뜻하지 않아요.

설계도에 등장하는 세 친구

  • 엔터티: 학생·강좌처럼 관리할 대상의 종류
  • 속성: 학생번호·이름처럼 기록할 항목
  • 관계: 학생이 강좌를 신청한다는 것처럼 대상 사이의 연결
↳ 다음 단원과 연결

세 친구는 다음 단원들에서 더 자세히 배워요. 지금은 「무엇을, 어떤 항목으로, 어떻게 연결해 관리할까?」 정도로 이해하면 충분해요.

02

02. 복잡한 현실을 이해하기 쉽게 바꿔요

학교 전체를 사진으로 찍은 것처럼 정보 하나하나를 모두 설계도에 옮길 필요는 없어요. 목적에 맞게 중요한 내용을 골라, 간단하고 분명하게 나타내는 것이 모델링의 특징이에요.

모델링의 세 특징
특징초등학생도 알 수 있는 뜻학교 사례
추상화중요한 공통점만 뽑아 생각하기민지·준호의 차이보다 「학생」이라는 공통 대상을 찾기
단순화필요한 요소로 복잡함 줄이기학생 관리에 불필요한 교실 벽 색깔은 모델에서 빼기
명확성누가 읽어도 같은 뜻으로 이해하도록 하기「신청」이 학생의 강좌 등록이라는 뜻임을 분명히 정하기

기억법 「추·단·명」 = 추상화 · 단순화 · 명확성 (STUDY.note 비공식 암기법)

! 헷갈리기 쉬워요

추상화와 단순화는 모두 세부를 줄이는 면이 있어요. 다만 추상화는 공통된 본질을 뽑는 데, 단순화는 복잡도를 낮추는 데 초점을 맞춰 이해하세요. 꼭 필요한 업무 규칙까지 없애면 좋은 모델이 아니에요.

03

03. 세 가지 질문으로 업무를 살펴봐요

학교에서 온라인 수강신청을 만든다면, 정보만 생각해서도 안 되고 어떤 일이 일어나는지만 생각해서도 안 돼요. 세 가지 질문을 함께 던지면 좋아요.

데이터 모델링에서의 세 관점
관점핵심 질문학교의 수강신청
데이터 관점 (What)어떤 데이터를 관리하지?학생 · 강좌 · 수강신청
프로세스 관점 (How)업무가 어떻게 진행되지?수강 신청 · 취소 · 확인
데이터와 프로세스의 상관 관점 (Interaction)업무가 어떤 데이터를 읽고 바꾸지?신청할 때 학생과 강좌를 확인하고 신청 기록을 추가

예를 들어 「수강신청」 버튼을 누르는 순간을 생각해 봐요. 학생과 강좌 정보가 있는지 확인하고, 문제가 없으면 수강신청 기록을 새로 남겨요. 이처럼 업무 처리와 데이터의 연결을 보는 것이 상관 관점이에요.

기억법 「데·프·상」 = 데이터 관점 · 프로세스 관점 · 상관 관점 (비공식 암기법)

! 관점을 나누되 따로 놀지 않아요

데이터 관점의 What과 프로세스 관점의 How는 이해를 돕는 질문이에요. 실제 업무 분석에서는 세 관점을 함께 고려해요.

04

04. 설계에도 순서가 있어요

집을 만들 때 먼저 방이 몇 개 필요한지 생각하고, 방의 배치를 자세히 정한 다음, 실제 재료와 시공 방법을 정하죠? 데이터 모델링도 큰 그림에서 자세한 설계로 나아가요.

세 가지 모델링 단계
단계핵심 질문학교 사례
개념적 모델링무엇을 관리해야 하지?학생·강좌·수강신청 같은 주요 대상을 도출하고 큰 관계 파악
논리적 모델링어떤 항목·관계·규칙이 있지?학생번호·강좌번호·신청일, 식별자와 관계, 정규화 등을 구체화
물리적 모델링선택한 DBMS에 어떻게 구현하지?테이블 이름·열 데이터 타입·제약조건·인덱스·저장 특성 고려
↳ 정확히 알아두기

개념적 단계는 업무 중심으로 넓게, 논리적 단계는 데이터 구조를 더 정확하게, 물리적 단계는 실제 DBMS 환경을 고려해 설계해요. 같은 업무를 세 수준에서 다르게 표현하는 거예요.

기억법 「개→논→물」 = 개념적 → 논리적 → 물리적 모델링

! 오개념 주의

물리적 모델링을 한다고 해서 반드시 직접 SQL을 작성하는 것만 뜻하지는 않아요. DBMS 특성과 데이터 타입·인덱스·제약조건 등을 고려한 설계가 핵심이에요.

05

05. 또 다른 3단계! 데이터베이스 스키마

앞에서는 「데이터를 설계하는 순서」를 배웠어요. 이번에는 이미 사용하는 데이터베이스를 어떤 높이에서 바라보는지에 따른 구조를 알아볼 거예요. 이름이 비슷해도 서로 다른 구분이에요.

스키마(Schema)는 데이터가 어떤 구조로 구성되는지를 설명하는 설계 정보예요. 세 층으로 나누면 보는 사람에게 필요한 모습, 조직 전체 모습, 실제 저장 모습을 구분할 수 있어요.

외부·개념·내부 스키마
계층무엇을 설명하나요?학교 사례
외부 스키마특정 사용자·프로그램에 필요한 데이터의 모습학생용 수강 목록, 담당자용 신청 현황
개념 스키마조직 전체 데이터의 통합된 논리 구조학생·강좌·수강신청의 전체 구조와 관계
내부 스키마데이터 저장과 접근에 관련된 물리적 구조저장 파일·페이지 배치·인덱스 등
↳ 조금 더 정확하게

외부 스키마는 사용자에 따라 여러 개일 수 있어요. 개념 스키마는 조직 전체 데이터를 바라보는 통합 관점이에요. 「외부 스키마 = SQL의 VIEW 명령으로 만든 객체」라고 항상 같은 뜻으로 보면 안 돼요.

! 가장 중요한 구분

「개념적→논리적→물리적 모델링」은 설계의 단계, 「외부→개념→내부 스키마」는 데이터베이스를 보는 계층이에요. 두 개를 같은 3단계라고 외우지 마세요.

06

06. 안쪽이 바뀌어도 바깥쪽은 그대로!

학교에서 서류를 보관하던 서랍을 더 큰 서랍으로 바꿨다고 학생의 수강 목록 자체가 달라져야 할까요? 아니겠죠. 데이터를 저장하는 방법과 사용자가 보는 구조를 분리하면 변경의 영향을 줄일 수 있어요.

데이터 독립성 비교
구분바뀌는 쪽변경 영향에서 보호하려는 쪽예시
물리적 데이터 독립성내부 스키마 (저장 구조)개념 스키마저장 파일 배치나 인덱스를 바꿔도 학생·강좌 논리 구조 유지
논리적 데이터 독립성개념 스키마 (전체 논리 구조)외부 스키마·응용 프로그램전체 구조에 필요한 속성을 추가해도 기존 사용자 화면이 영향받지 않도록 유지
↳ 정확한 정의

물리적: 내부 변경 → 개념 구조를 보호. 논리적: 개념 변경 → 외부 사용자 관점을 보호. 두 독립성은 각각 계층 사이의 대응(매핑)을 통해 지원돼요.

! 항상 100% 보장은 아니에요

데이터 독립성이 있다고 모든 변경이 자동으로 아무 영향 없이 이루어지는 건 아니에요. 화면이 필요로 하는 필드를 없애면 응용 프로그램을 바꿔야 할 수도 있어요. 목표는 영향을 줄이거나 분리하는 것이에요.

기억법: 「물리=저장법 바꿈」, 「논리=전체 구조 바꿈」. 어느 쪽을 바꿔도 한 단계 위의 영향이 줄어드는지 확인!

07

07. 좋은 설계와 나쁜 설계를 비교해요

모델링은 정보를 보기 좋게 그리는 것으로 끝나지 않아요. 여러 사람이 오랫동안 써도 잘못된 결과가 나오지 않도록 설계해야 해요.

모델링의 대표적인 유의사항
주의할 점문제 사례더 나은 방향
불필요한 중복학생의 연락처를 신청 기록마다 따로 적어 고칠 곳이 많아짐학생 정보를 한 곳에서 관리하고 필요할 때 연결
비유연성수업 이름이 바뀔 때 신청 기록 구조까지 일일이 바꿔야 함바뀔 수 있는 업무와 데이터 구조를 지나치게 묶지 않기
비일관성어느 기록에는 「취소」, 다른 기록에는 「신청 중」으로 상충값의 의미와 데이터 사이 규칙을 명확히 정하기

좋은 데이터 모델은 무엇을 갖춰야 할까요?

  • 완전성: 업무에 필요한 데이터를 빠뜨리지 않기
  • 중복 배제: 같은 사실의 불필요한 반복 저장을 피하기
  • 업무 규칙: 학원에서 한 강좌 정원을 넘으면 신청할 수 없는 등의 규칙을 명확히 표현하기
  • 데이터 재사용: 한 업무 화면에만 묶이지 않고 필요한 여러 곳에서 활용하기
  • 의사소통: 사용자와 개발자가 같은 뜻으로 읽을 수 있도록 하기
  • 통합성: 조직 전체에서 같은 데이터를 공통 의미로 정의·관리하기
! 시험 원칙과 실무 예외

실제 시스템에서는 성능 등의 이유로 일부 데이터를 중복 저장할 수도 있어요. 여기서는 기본 설계에서 의미 없는 중복을 줄여야 한다는 원칙을 배워요.

08

08. 관계를 그림으로 그려 봐요

학생, 강좌, 수강신청이라는 세 종류의 정보를 정했다면, 이제 어떤 정보가 서로 연결되는지 그려 볼 차례예요. 이 그림이 ERD(Entity Relationship Diagram, 개체-관계 다이어그램)예요.

ERD는 엔터티와 그 사이의 관계를 나타내는 도식이에요. 사람들과 데이터 구조를 함께 확인하고, 빠진 관계나 잘못된 업무 규칙을 찾는 데 도움을 줘요.

입문용 ERD 작성 6단계

  • ① 엔터티를 찾고 그림으로 표시해요.
  • ② 보기 쉽도록 엔터티를 배치해요.
  • ③ 엔터티 사이의 관계를 연결해요.
  • ④ 관계의 이름을 읽기 쉽게 붙여요.
  • ⑤ 한쪽과 다른 쪽이 몇 건씩 연결되는지(관계 차수)를 표현해요.
  • ⑥ 반드시 연결돼야 하는지, 연결 없이도 될 수 있는지(필수·선택)를 표시해요.
↳ 그림 속 규칙은 예시

이 예제에서는 수강신청 1건이 학생 1명과 강좌 1개를 연결한다고 가정해요. 실제 ERD에서 관계 차수와 필수·선택 여부는 업무 규칙을 확인한 뒤 결정해야 해요.

! 다음 단원 예고

Chen 표기법과 IE(Crow’s Foot) 표기법은 모양이 달라요. 이 페이지는 ERD의 역할과 순서를 이해하는 것이 목적이고, 정확한 관계선 기호는 「관계」 단원에서 배워요.

09

09. 오늘의 한 장 요약

  • 모델링: 관리할 데이터의 의미·구조·관계를 미리 설계하기
  • 특징: 추상화·단순화·명확성 (추단명)
  • 관점: 데이터 What · 프로세스 How · 상관 Interaction (데프상)
  • 설계 단계: 개념적 → 논리적 → 물리적 (개논물)
  • 스키마 구조: 외부(사용자별 관점) → 개념(전체 논리 구조) → 내부(저장 구조)
  • 독립성: 물리적(내부 변경에 대해 개념 보호), 논리적(개념 변경에 대해 외부 보호)
  • 좋은 모델: 중복·비유연성·비일관성에 주의하고 업무 규칙을 분명히 표현
  • ERD: 엔터티를 그려 연결하고 관계명·차수·필수 여부를 기록
↳ 시험 직전 확인

이름에 「개념」이 들어가도 「개념적 모델링」과 「개념 스키마」는 다른 분류예요. 설계 순서인가? 보는 계층인가? 먼저 질문하면 혼동이 줄어요.
