TCLTransaction Control Language

개념부터 차근차근!

변경을 확정할까요, 되돌릴까요? TCL

앞 단원 06AB에서는 데이터를 INSERT·UPDATE·DELETE했습니다. 이제 여러 변경을 하나의 작업으로 묶고 안전하게 확정하거나 취소하는 방법을 배워요.

COMMIT은 트랜잭션을 확정, ROLLBACK은 전체 취소, ROLLBACK TO는 SAVEPOINT 이후만 취소합니다. 안쪽 RELEASE는 최종 COMMIT이 아니며, 변경 가시성·자동 커밋·DDL 동작은 DBMS 및 거래 경계를 함께 확인해야 합니다.

이 단원을 끝내면

  1. 1트랜잭션이 여러 DML을 하나의 원자적 작업으로 묶는 이유와 ACID 네 특성을 설명해요.
  2. 2COMMIT과 ROLLBACK을 적용한 최종 데이터를 계산해요.
  3. 3SAVEPOINT, ROLLBACK TO, RELEASE가 서로 다르게 작동하는 이유를 SQL 순서로 추적해요.
  4. 4서로 다른 DB 연결이 미커밋 데이터와 커밋 후 데이터를 어떻게 보는지 구별해요.
  5. 5더티 리드·반복 불가능 읽기·팬텀 리드를 정의하고 DBMS별 격리 차이를 인식해요.
  6. 6Oracle과 SQLite의 DDL 자동 커밋·트랜잭션 취소 차이를 설명해요.
  7. 7예상되는 SQL 제약 오류가 항상 트랜잭션 전체 취소를 뜻하지 않는다는 점을 알아요.
학습 기록을 불러오는 중이에요.
01

01. 학생 정보 변경을 안전하게 확정하려면?

학생의 학습시간을 수정하다가 다른 학생의 정보도 잘못 바꾸었다면 어떻게 할까요? TCL(Transaction Control Language)은 여러 변경을 하나의 작업 단위로 묶고, 확정하거나 되돌리는 명령을 다룹니다. DML이 데이터를 바꾸는 작업이라면, TCL은 그 변경을 확정·취소하는 흐름을 다룹니다.

모든 SQL 실습에서 새로 시작하는 학생 5명
학생 ID이름학습시간
S101민지5
S102준호7
S103서연8
S104지훈9
S105유나6
계좌 이체 예시 — 변경 전
계좌 A계좌 B총합
100100200
↳ 변경과 확정은 별개

BEGIN; UPDATE ...; COMMIT;은 변경을 확정하고, BEGIN; UPDATE ...; ROLLBACK;은 확정 전 변경을 취소합니다. SQLite 실행 예제 A1·A2를 보세요.

! SELECT와 TCL은 다른 역할

SELECT는 읽기 SQL입니다. BEGIN·COMMIT·ROLLBACK은 트랜잭션 경계를 제어합니다. 명령의 분류 관례는 교재별로 일부 차이가 있을 수 있습니다.

02

02. 왜 여러 SQL을 하나의 거래로 묶을까요? ACID

한쪽 계좌에서 30을 빼고 다른 쪽 계좌에 30을 더하는 두 SQL은 하나의 이체입니다. 앞 문장만 반영되고 뒷 문장이 실패하면 잔액 총합이 200에서 170으로 잘못 바뀔 수 있습니다. 따라서 두 작업을 한 트랜잭션으로 묶습니다.

트랜잭션의 네 가지 특성
ACID쉬운 뜻정확한 핵심
Atomicity 원자성모두 처리하거나 모두 취소트랜잭션의 원자적 완료/중단
Consistency 일관성유효한 규칙을 지키는 상태제약·트랜잭션 로직으로 정의한 불변조건 보존
Isolation 격리성다른 거래의 중간 변경과 분리DBMS 및 격리 수준에 따라 보장 범위 다름
Durability 지속성확정된 변경을 보존커밋 완료 후 장애에도 복구될 수 있도록 보장
↳ 예제 A2

계좌 A=100, B=100 → A=70, B=130 → COMMIT. 합계는 200입니다.

! 일관성은 시스템이 자동으로 모든 업무 규칙을 알아서 지킨다는 뜻이 아닙니다

잔액 합계 200 같은 업무 규칙은 올바른 변경 로직과 필요한 제약·동시성 처리가 뒷받침해야 합니다. ACID 설명을 만능 데이터 오류 방지로 해석하지 마세요.

03

03. COMMIT은 무엇을 확정할까요?

COMMIT은 현재 트랜잭션을 종료하며 변경을 확정합니다. 같은 연결 A는 커밋 전에 자신이 수정한 값을 읽을 수 있지만, 별도 연결 B는 일반적인 기본 격리 설정에서 미확정 값을 읽지 못합니다.

B1: S101의 학습시간
관찰 시점연결 A연결 B
변경 전55
A가 11로 UPDATE 후, COMMIT 전115
A의 COMMIT 뒤 새 조회1111
↳ 실습 B1, B2, B4

한 행 수정, INSERT, 두 계좌 이체가 각각 COMMIT 뒤 확정됩니다. A·B는 서로 다른 SQLite 연결입니다.

! 영원히 취소 불가?

확정된 변경은 해당 트랜잭션의 ROLLBACK으로는 취소할 수 없습니다. 이후 보상 트랜잭션을 실행하거나 적절한 백업/복구를 이용하는 것은 별개의 작업입니다.

04

04. ROLLBACK은 어디까지 되돌릴까요?

저장점을 지정하지 않은 ROLLBACK은 현재 트랜잭션 전체의 미확정 변경을 취소합니다. UPDATE뿐 아니라 INSERT와 DELETE로 수행한 행 변경도 되돌릴 수 있습니다.

실습 C1~C5 실제 결과
상황ROLLBACK 후
S101을 99로 변경원래 5
S106 INSERT학생은 5명
S105 DELETES105 복원
계좌 A=0, B=200A=100, B=100
WHERE 없는 5명 전체 UPDATE기존 각 학습시간 복원
↳ 앞 단원 DML과 연결

DML의 WHERE 누락은 위험하지만, 아직 COMMIT되지 않은 동일 트랜잭션 내부라면 전체 취소가 가능합니다.

! 자동 커밋과 클라이언트 설정

단일 UPDATE가 자동 커밋된 뒤에는 새 ROLLBACK으로 되돌릴 수 없습니다. 클라이언트의 자동 커밋·연결 설정을 확인해야 합니다.

05

05. SAVEPOINT로 일부만 취소할 수 있을까요?

SAVEPOINT sp1은 현재 트랜잭션 안의 중간 지점을 표시합니다. ROLLBACK TO sp1은 저장점 이후 변경을 되돌리고, 그 이전 변경을 남깁니다. 명시적 BEGIN으로 시작한 트랜잭션은 계속 열려 있습니다.

실습 D1 — SAVEPOINT 전과 후의 수정
순서변경최종 반영
1S101: 5→11유지
2SAVEPOINT sp1취소 기준
3S102: 7→99취소
4ROLLBACK TO sp1; RELEASE sp1; COMMITS101=11, S102=7
↳ 코드

BEGIN; UPDATE ...S101...; SAVEPOINT sp1; UPDATE ...S102...; ROLLBACK TO sp1; RELEASE sp1; COMMIT; — 정확한 SQL은 D1에 있습니다.

! SAVEPOINT에 대한 두 문장의 차이

ROLLBACK TO sp1은 sp1 이후 변경을 취소하지만 저장점 자체는 유지합니다. RELEASE sp1은 저장점을 제거하며, 그 자체가 바깥 트랜잭션을 확정하는 것은 아닙니다.

06

06. RELEASE와 COMMIT은 같을까요?

RELEASE SAVEPOINT는 지정한 저장점과 그보다 안쪽의 활성 저장점을 제거합니다. 바깥 트랜잭션이 남아 있다면 RELEASE 뒤에도 ROLLBACK이 전체 변경을 취소할 수 있습니다.

동일한 변경을 다른 종료 방식으로
실습종료 순서S101 최종값
E1BEGIN → SAVEPOINT → UPDATE 99 → RELEASE → ROLLBACK5
E2BEGIN → SAVEPOINT → UPDATE 99 → RELEASE → COMMIT99
E3 (SQLite)최외곽 SAVEPOINT → UPDATE 55 → RELEASE55
↳ SQLite 최외곽 규칙

SQLite에서는 별도 BEGIN 없이 만들어진 최외곽 SAVEPOINT의 RELEASE가 트랜잭션을 확정합니다. 안쪽 SAVEPOINT의 RELEASE는 최종 확정이 아닙니다.

! 다른 DBMS와 정확히 구분

PostgreSQL은 SAVEPOINT를 트랜잭션 블록 내부에 두어야 합니다. SQL Server는 SAVE TRANSACTION이라는 별도 구문을 사용합니다. SQLite의 최외곽 SAVEPOINT 사례를 모든 DBMS 규칙으로 일반화하지 않습니다.

07

07. 두 사용자가 동시에 같은 데이터를 보면?

서로 독립된 연결 A와 B가 같은 DB 파일을 읽습니다. A가 S101을 5→11로 변경해도 A가 COMMIT하기 전 B는 5를 읽습니다. 이것은 SELECT를 두 번 실행했다는 사실만으로 보장되는 것이 아니라, 서로 다른 연결과 트랜잭션 경계가 있어서 가능한 동작입니다.

G1·G3 — 서로 다른 두 사례
실습연결 B가 보는 순서조건
G15 → 11B의 별도 문장 조회, A 커밋 전후
G35 → 5 → 11B가 WAL 읽기 트랜잭션을 유지했다가 끝낸 후 새 조회
↳ 재현 조건

G3는 SQLite의 WAL 저널 모드에서 검증합니다. 다른 DBMS의 읽기 일관성은 격리 수준과 MVCC 구현에 따라 다를 수 있습니다.

! 같은 연결 안에서는 자기 미커밋 변경을 읽을 수 있음

A에서 UPDATE한 뒤 A로 SELECT하면 11입니다. B의 5와 혼동하지 마세요. 실습 G1을 참조하세요.

08

08. 격리 수준과 동시성 문제를 구별해요

격리 수준은 동시에 수행되는 트랜잭션이 서로의 데이터를 어떻게 볼지 정하는 정책입니다. SQL 표준에서 설명하는 대표 이상 현상은 더티 리드(미확정 변경 읽기), 반복 불가능 읽기(같은 행 재조회 결과 변화), 팬텀 리드(조건에 맞는 행 집합 변화)입니다.

전형적인 이상 현상
이름예시주의
Dirty readA가 아직 COMMIT하지 않은 11을 B가 읽음일반 SQLite 별도 연결 기본 설정에서는 불가
Non-repeatable readB가 같은 S101 행을 읽었더니 값이 바뀜하나의 트랜잭션 범위와 격리 수준에 좌우
Phantom read같은 조건으로 조회했더니 행 개수가 바뀜단순 같은 행 재조회와 구별
↳ SQLite 실습 G3·G4

WAL에서 B가 읽기 트랜잭션을 유지하는 동안 A가 커밋해도 B는 기존 스냅샷을 봅니다. G4에서는 동시 쓰기 시작이 잠금 오류를 냅니다.

! 표준 격리 수준 이름만으로 모든 DBMS 결과를 단정하지 않습니다

READ COMMITTED, REPEATABLE READ, SERIALIZABLE 등의 실제 보장은 DBMS마다 다를 수 있습니다. 특히 SQLite의 동시 쓰기 직렬화와 WAL 스냅샷을 다른 제품의 기본 격리 동작으로 일반화하지 마세요.

09

09. DDL을 실행하면 COMMIT이 자동으로 될까요?

Oracle과 SQLite/PostgreSQL의 DDL 트랜잭션 동작을 구별해야 합니다. Oracle 19c에서는 DDL을 실행할 때 앞선 변경을 암묵적으로 COMMIT하며, 성공한 DDL 뒤에도 COMMIT이 수행됩니다. 반면 SQLite에서는 명시적 트랜잭션 안의 CREATE TABLE·ALTER TABLE·CREATE INDEX를 ROLLBACK할 수 있습니다.

DBMS별 구분
환경DDL·트랜잭션 핵심검증 상태
Oracle 19c문법상 유효한 DDL 전 암묵적 COMMIT, 성공 DDL 뒤도 COMMIT공식 문서 대조 / 서버 미실행
SQLite 3.46.1BEGIN 안에서 CREATE TABLE 후 ROLLBACK으로 취소 가능H1~H5 실제 실행
PostgreSQL 18일반 CREATE TABLE 등은 트랜잭션 블록에서 취소 가능(예외 명령 별도 확인)공식 문서 참고 / 서버 미실행
↳ SQLite H1 vs H2

H1은 CREATE TABLE 후 ROLLBACK해서 테이블이 없어집니다. H2는 COMMIT해서 생성된 테이블이 남습니다.

! DDL이라고 다 같은 결과가 아닙니다

Oracle에서 DDL 앞의 미확정 DML은 암묵적 COMMIT의 영향을 받을 수 있습니다. PostgreSQL도 모든 DDL 명령이 임의의 트랜잭션에서 허용된다는 뜻은 아닙니다. SQLD에서는 문맥과 DBMS를 먼저 확인하세요.

10. 시험에서 어디를 먼저 구별할까요?

문제 속 SQL의 순서·트랜잭션 경계·DBMS·저장점의 위치를 먼저 표시하면, 마지막 값이 무엇인지 직접 계산할 수 있습니다.

시험 판단 순서
확인할 것핵심 질문
① BEGIN 여부명시적 거래인가, 자동 커밋인가?
② UPDATE/INSERT/DELETE어떤 데이터가 변경되었나?
③ SAVEPOINT어디부터 되돌리는가?
④ ROLLBACK TO vs ROLLBACK일부 취소인가 전체 취소인가?
⑤ RELEASE vs COMMIT저장점만 제거했나, 거래를 확정했나?
⑥ 서로 다른 세션미확정 값이 다른 연결에 보이는가?
⑦ DBMS DDLOracle 자동 커밋인지, SQLite에서 취소 가능한 DDL인지?
↳ 자체 예상 중요도

COMMIT/ROLLBACK과 저장점은 개념 학습의 우선순위를 높게 설정했습니다. 실제 시험 출제 빈도를 집계한 근거는 아니므로 ‘빈출’이라고 단정하지 않습니다.

12. TCL 핵심 요약

  • COMMIT: 현재 트랜잭션 변경을 확정하고 종료합니다.
  • ROLLBACK: 현재 트랜잭션 전체의 미확정 변경을 취소합니다.
  • SAVEPOINT: 트랜잭션 내 중간 되돌림 지점을 만듭니다.
  • ROLLBACK TO: 저장점 이후 변경만 취소하며 해당 저장점은 유지됩니다.
  • RELEASE: 저장점을 없앱니다. 안쪽 RELEASE는 바깥 COMMIT이 아닙니다.
  • 다른 연결: 일반 설정에서 미커밋 변경은 보이지 않습니다.
  • DDL: Oracle의 암묵적 COMMIT과 SQLite의 트랜잭션 내 DDL 취소를 구분합니다.
