모델이 표현하는 트랜잭션의 이해Business Transactions in Data Models

개념부터 차근차근!

주문 한 건은 왜 여러 데이터 변경을 함께 묶을까요?

쇼핑몰에서 주문 버튼 한 번을 누르면 주문 한 건, 주문상세 여러 건, 재고 수량이 함께 바뀔 수 있어요. 어느 데이터까지 반드시 함께 성공해야 하고 모델은 어떤 업무 규칙을 표현해야 할까요?

업무 트랜잭션은 함께 처리되어야 하는 업무 작업 단위이고, 데이터 모델은 그 과정의 엔터티·관계·필수/선택·배타·무결성 조건을 표현해요. 실행 단계의 BEGIN·COMMIT·ROLLBACK은 여러 DB 변경을 한 단위로 처리하도록 돕지만, 모델의 업무 규칙을 모두 자동으로 구현하지는 않아요.

이 단원을 끝내면

  1. 1주문 한 건처럼 업무적으로 함께 완결되어야 하는 작업을 찾고 SQL 한 문장과 구별할 수 있어요.
  2. 2주문·상세·재고 등 여러 테이블의 변경을 성공 또는 취소의 한 경계로 묶어야 하는 이유를 설명해요.
  3. 3주문상세의 필수·선택 참여와 주문 상태에 따른 최소 수량 규칙을 구별할 수 있어요.
  4. 4개인고객/법인고객 중 하나만 선택하는 배타적 관계와 그 검증 방법을 설명해요.
  5. 5PK·FK·CHECK·UNIQUE·트랜잭션 경계의 책임을 구분하고 주문 성공/실패의 상태를 예측할 수 있어요.
학습 기록을 불러오는 중이에요.
01

01. 주문 버튼 한 번에 무엇이 바뀔까요?

예를 들어 구매자 U01이 주문 O801을 완료하면 주문 헤더 1건, 주문상세 2건, 상품 재고 2종의 감소가 하나의 업무에 포함될 수 있어요. 주문ID와 상세행을 서로 연결하고, 일부만 저장되지 않도록 처리 경계를 정해야 해요.

가상 주문의 업무 사실
대상예시 값의미
구매자U01주문 주체
주문O801한 번의 주문
주문상세O801/1=P01 2개, O801/2=P02 1개구매 품목
초기 재고P01=10개, P02=5개확정 시 각각 차감
↳ 새 시나리오

앞 단원의 학생 S101·신청 E501 예제와는 별도의 주문 업무예요. 관계·키·JOIN을 이미 배웠기 때문에 이번에는 주문 헤더/상세와 재고를 연결해 한 업무의 변화로 살펴봐요.

! 오개념 주의

하나의 주문 업무가 SQL 한 문장만으로 끝나야 한다는 뜻은 아니에요. 반대로 SQL 문장 여러 개라고 항상 같은 업무 트랜잭션으로 묶어야 하는 것도 아니에요.

02

02. 업무 트랜잭션은 어떻게 정하나요?

업무 트랜잭션은 업무적으로 한 번에 완성되거나 취소되어야 하는 일의 묶음이에요. 주문 확정이라는 하나의 목적을 달성하려면 주문 기록·상세 기록·재고 반영 등이 일관되게 완료되어야 한다고 가정해 볼게요.

업무 목적과 단위
업무함께 처리할 변경의 예판단 근거
주문 확정주문 1건 + 상세 2건 + 재고 차감중간에 실패하면 불완전한 주문이 됨
상품 설명 수정상품명 1곳 수정주문 확정과는 다른 업무 목적
이미 확정된 주문 조회SELECT 조회쓰기 트랜잭션 예제와 별도 행위
↳ 범위 결정

동시에 성공해야 할 작업의 범위는 실제 업무 규칙에서 정해야 해요. 결제·배송 연동까지 항상 단일 DB 트랜잭션으로 묶는 것은 아니며, 외부 시스템은 별도의 설계가 필요할 수 있어요.

! 오개념 주의

ERD의 관계선만으로 트랜잭션 경계가 자동 결정되지는 않아요. 업무 단계와 프로그램의 실행 경계는 별도로 설계해야 해요.

03

03. 여러 데이터 변경이 절반만 성공하면 어떻게 될까요?

한 주문을 처리하다 재고가 부족해졌는데 주문·상세만 남으면 없는 재고를 판매한 상태가 될 수 있어요. 이 사례에서는 주문/상세 INSERT와 재고 UPDATE가 모두 성공할 때 COMMIT, 실패하면 명시적으로 ROLLBACK하도록 업무를 구성해요.

주문 O801의 정상 처리
변경 대상처리 전COMMIT 후
주문 O801없음CONFIRMED 1건
주문상세 O801/1, O801/2없음2건
P01 재고108
P02 재고54
↳ 실행 예제의 범위

DBMS의 BEGIN·COMMIT·ROLLBACK은 다수 변경을 하나의 DB 트랜잭션으로 처리해요. SQLite에서는 오류 하나가 발생했다고 이전 문장이 항상 자동으로 전부 취소되는 것은 아니므로, 애플리케이션이 적절히 실패를 감지하고 ROLLBACK을 해야 해요.

! 오개념 주의

각 INSERT/UPDATE를 자동 커밋하여 처리하면 중간 오류 뒤 이전 변경이 이미 확정될 수 있어요. 트랜잭션 원자성을 설명할 때는 같은 명시적 경계에 포함된 변경을 기준으로 해요.

04

04. 주문과 주문상세는 언제 필수 관계일까요?

이 가상 업무에서는 주문이 초안(DRAFT)일 때 상세가 0건이어도 괜찮고, 확정(CONFIRMED)할 때는 상세가 최소 1건 있어야 해요. 각 상세는 반드시 하나의 주문에 속한다고 가정해요.

참여 규칙과 데이터 모델
규칙 주체최소~최대해석
초안 주문 → 상세0..N상세가 하나도 없을 수 있음
확정 주문 → 상세1..N확정 시 최소 1개 필요
상세 → 주문1..1상세는 부모 주문을 반드시 참조
↳ 제약의 방향

상세의 order_id NOT NULL REFERENCES orders(order_id)는 상세→주문 1건 존재를 강제하는 데 도움이 돼요. 그러나 부모 주문에 상세가 최소 1건인지까지 단순 FK 하나가 보장하지는 않아요. 확정 시점에 별도의 검증이 필요해요.

↳ ERD 표기법 연결

사용자 제공 압축정리의 IE 표기에서는 선택 참여를 원(O)으로, Barker 표기에서는 선택 관계를 점선으로 설명해요. 표기법의 선·기호를 데이터가 언제 확정되는지 또는 SQL COMMIT과 혼동하지 마세요. 실제 관계의 최소·최대 참여 수는 함께 확인해야 해요.

! 오개념 주의

선택 관계는 “항상 NULL을 저장한다”는 말이 아니에요. 주문에 상세가 없을 수 있다는 규칙과 상세의 order_id를 NULL로 허용할지는 다른 문제예요.

05

05. 개인고객 또는 법인고객 중 하나만 선택한다면?

별도 모델 예제에서 주문은 개인고객 또는 법인고객과 연결되며 정확히 한쪽에만 연결된다고 가정해요. 이렇게 서로 동시에 성립할 수 없는 참조를 배타적(XOR) 관계라고 설명해요.

배타적 관계의 허용 여부
개인고객 FK법인고객 FK판정
U01NULL유효: 개인 주문
NULLB01유효: 법인 주문
U01B01잘못됨: 두 고객 유형 모두 연결
NULLNULL잘못됨: 둘 중 어느 쪽도 연결하지 않음
↳ 서로 다른 모델 대안

이것은 주문 O801의 기본 buyer_id 구조와 구분해서 비교하는 대안 모델이에요. 이 예제처럼 두 FK를 둔다면 CHECK ((personal_id IS NOT NULL) <> (business_id IS NOT NULL))처럼 정확히 하나만 설정되도록 강제할 수 있어요. 양쪽 FK도 참조 무결성을 갖춰야 해요.

! 오개념 주의

배타적 관계는 여러 데이터 변경을 한 번에 성공시키는 원자성과 다른 개념이에요. ERD에 XOR 기호를 그렸다고 DB가 자동으로 두 FK의 중복 선택을 막는 것도 아니에요.

06

06. 어떤 제약이 주문 데이터의 정확성을 지킬까요?

주문 헤더·상세·상품을 따로 저장하려면 식별자(PK), 부모 참조(FK), 수량 검사(CHECK) 등을 설계해요. 그러나 이 제약만으로 “주문 확정 때 상세가 최소 하나”라는 모든 업무 규칙이나 주문·재고 변경의 묶음 성공까지 자동으로 해결되지는 않아요.

업무 규칙별 책임
업무 규칙적합한 구현 수단주의할 점
상세 (order_id,line_no) 중복 금지복합 PK같은 주문에서 상세 번호 중복 방지
상세는 존재하는 주문을 참조FK + NOT NULL부모 없는 상세 방지
수량은 1 이상, 재고는 0 이상CHECK검사 대상 행의 값 확인
확정 주문에는 상세 1개 이상업무 검증/추가 제약 또는 트리거일반적인 상세 FK만으로 불충분
주문·상세·재고 변경 함께 성공DB 트랜잭션 경계PK/FK 제약만으로 보장하지 못함
! 오개념 주의

외래키는 한쪽에서 다른 쪽을 참조하도록 하는 제약이에요. “주문은 항상 상세를 갖는다”는 부모 쪽 최소 참여 수를 FK 하나로 자동 보장한다고 설명하면 틀려요.

07

07. ERD의 규칙은 SQL의 어디에 반영될까요?

모델의 엔터티는 테이블, 식별자는 PK, 필수 참조는 NOT NULL FK, 수량 제약은 CHECK 같은 물리적 제약으로 옮길 수 있어요. 한 주문 업무를 확정할 때 여러 SQL을 한 번에 처리하는 트랜잭션 경계는 별도로 지정해요.

모델 → SQL 연결
모델 수준물리 DB 수준실행 수준
주문과 상세 관계order_lines.order_id FKINSERT 순서와 묶음 처리
상세 번호와 수량PK(order_id,line_no), CHECK(qty>0)중복·잘못된 수량 실패 처리
초안/확정 상태와 최소 상세status CHECK + 확정 시 건수 검증확정 전에 검증 후 COMMIT
재고 수량products.stock CHECK(stock>=0)UPDATE 성공 여부 확인·실패 시 ROLLBACK
↳ DBMS별 실행 주의

SQLite에서는 PRAGMA foreign_keys=ON을 트랜잭션 시작 전에 설정해요. 개별 오류가 전체 트랜잭션을 무조건 자동 취소한다고 가정하지 않고, 실패 시 명시적 ROLLBACK을 실행하는 예제를 제공해요.

! 오개념 주의

“트랜잭션이 있으니 모든 업무 제약도 자동으로 맞는다”는 오개념을 피하세요. 트랜잭션은 함께 확정/취소되는 단위, PK/FK/CHECK와 업무 코드는 무엇을 허용할지를 다뤄요.

08

08. 성공·실패 주문을 비교해 봐요

O801은 상품 P01 2개(단가 12,000), P02 1개(단가 8,000)를 구매하는 주문이에요. 상품 재고가 충분하면 합계 32,000과 상세 두 행, 재고 변화 P01 10→8·P02 5→4가 함께 확정돼요.

정상 주문 O801 결과
항목COMMIT 후
주문 O801CONFIRMED, 총액 32000
상세 O801/1P01 × 2 × 12000
상세 O801/2P02 × 1 × 8000
재고P01=8, P02=4

실패 가상 주문 O802에서는 먼저 P02를 1개 차감한 다음, 남은 P01 재고 8개보다 많은 9개를 차감하려고 해요. 이때 오류를 발견하고 전체 트랜잭션을 ROLLBACK하면 O802 주문·상세는 남지 않고, 앞서 줄었던 P02 재고도 다시 4개가 돼요.

↳ 실습 파일

패키지 04_VERIFIED_SQLITE_EXAMPLE.sql과 05_SQLITE_TRANSACTION_CHECK.py를 통해 성공/실패 결과를 SQLite 메모리 DB에서 검증할 수 있어요. 교육 화면의 버튼은 실제 DB를 수정하는 것이 아니라 검증한 시나리오를 재현하는 가상 도식이에요.

! 오개념 주의

ROLLBACK은 그 트랜잭션 안의 아직 커밋되지 않은 변경을 취소해요. 과거에 이미 COMMIT한 주문 O801까지 함께 삭제하지 않아요.

09

09. 데이터 모델과 트랜잭션의 차이를 정리해요

  • 업무 트랜잭션: 업무적으로 한 번에 완결할 작업 단위, 한 SQL 문장과 반드시 1:1은 아니에요.
  • 엔터티·관계: 주문·상세·상품 등 업무 데이터가 어떻게 연결되고 제약되는지 표현해요.
  • 필수/선택: 부모가 반드시 자식을 가져야 하는지와 자식이 부모를 참조해야 하는지를 방향별로 생각해요.
  • 배타적 관계(XOR): 두 종류의 부모 중 정확히 하나를 선택하는 규칙을 업무 제약으로 표현해요.
  • PK·FK·NOT NULL·CHECK: 개별 데이터 무결성을 돕지만 모든 업무 검증과 원자적 실행까지 자동 보장하지는 않아요.
  • BEGIN/COMMIT/ROLLBACK: 여러 DB 변경을 같은 실행 경계로 묶고 실패하면 해당 트랜잭션 변경을 취소해요.
↳ 복습 기준

두 가지 질문을 나누면 쉬워요. “어떤 데이터가 유효한가?”(모델·제약)와 “여러 변경을 어떻게 함께 확정/취소하는가?”(트랜잭션 경계)예요.
